## 2. Цель

1. Команда действует от отдельного actor с минимальными разрешениями: без `administration`, `secrets`, `actions`, `workflows`, `members`.
2. Запись возможна только в ветки согласованных пространств имён; `main` и `develop` изменяются только через PR, который сливает владелец. Команда не может слить PR **даже после одобрения владельцем**.
3. Любая попытка выйти за границы отклоняется сервером и остаётся в журнале оценок правил (`rule-suites`).

## 3. Идентичность команды: варианты

### 3.1. Роль и разрешения токена — разные механизмы

Эффективные права запроса = роль actor в репозитории ∩ разрешения токена. Проверять нужно оба слоя отдельно (раздел 5), потому что:

- **Роль** (`read` / `triage` / `write` / `maintain` / `admin`) назначается пользователю-коллаборатору; у приложения роли нет — её заменяют разрешения установки.
- **Разрешения токена**: у fine-grained PAT — явный набор разрешений на выбранные репозитории, не шире роли пользователя; у installation token — разрешения установки приложения (`contents`, `pull_requests`, `metadata`, …), выданные владельцем при установке; у classic PAT — scopes (`repo` даёт всё, что даёт роль; для команды не используется).
- Роль `write` с токеном без `administration` **не** позволяет менять rulesets; роль `admin` с таким же токеном — тоже не позволяет через этот токен, но владелец-человек с ролью `admin` может сделать это из браузера. Поэтому отдельный actor нужен именно для того, чтобы у команды не было роли `admin` ни через какой токен.

## 4. Проект rulesets

Область действия rulesets задаётся списками `conditions.ref_name.include` / `exclude`: по документации REST API GitHub (Create a repository ruleset) `include` принимает имена или шаблоны ссылок, а также `~DEFAULT_BRANCH` и `~ALL`; `exclude` — имена или шаблоны, при совпадении с любым из которых условие не выполняется. Документация GitHub «Creating rulesets for a repository» описывает fnmatch с флагом `File::FNM_PATHNAME` для шаблонов веток и тегов: `*` не совпадает с `/`; произвольная глубина — `qa/**/*`. С полным или коротким именем ссылки сопоставляется шаблон, документация не уточняет; примеры REST используют `refs/heads/…`. Поведение на сервере подтверждается TC-D10-05. По модели документированного синтаксиса (Ruby `File.fnmatch` с `FNM_PATHNAME`) `refs/heads/docs/**` ведёт себя как одноуровневый `refs/heads/docs/*` и совпадает также с существующей веткой `docs/chg-0004` вне разрешения D-10 (§2: только `docs/arch-0001`); поэтому пространство имён команды в разделе 4.2 подлежит пересмотру решением владельца по CHG7-OD3 (OD3-2) до применения. Допустимые `actor_type` в `bypass_actors`: `Integration`, `OrganizationAdmin`, `RepositoryRole`, `Team`, `DeployKey`, `EnterpriseOwner`, `EnterpriseRole`, `User`. Оба ruleset — уровня репозитория, `target: branch`, `enforcement: active`.

### 4.2. `team-write-boundary` (новый)

| Параметр | Значение |
| --- | --- |
| `conditions.ref_name.include` | `["~ALL"]` — все ветки, **включая `refs/heads/main` и `refs/heads/develop`** |
| `conditions.ref_name.exclude` | `["refs/heads/docs/**", "refs/heads/impl/**"]` — пространства имён команды; `fix/**`, `feature/**`, `release/**` намеренно не исключены (см. ниже) |
| `rules` | `creation`, `update`, `deletion` |

Числовой `actor_id` роли admin документацией не перечислен; берётся из ответа `GET /repos/{o}/{r}/rulesets/{id}` после создания записи владельцем в интерфейсе, не из памяти |
| Эффект для actor команды (без роли `admin`) | Нельзя создать, обновить или удалить любую ветку вне `docs/**` и `impl/**`. Слияние PR в `develop` — это `update` ветки `develop` от actor команды → отклоняется **независимо от одобрения владельцем**. Push в `feature/**`, `release/**`, `fix/**` отклоняется до решения владельца о расширении пространства имён |

Почему `fix/**` не включён: по CLAUDE.md §12 `fix/*` — ветки исправлений дефектов; команда пока не получала разрешения на такие работы, а каждое расширение пространства имён — решение владельца (раздел 7). `docs/**` шире, чем действующее «только `docs/arch-0001`» (D-10 §2): ограничение до одной ветки rulesets выразить можно (`refs/heads/docs/arch-0001` вместо `refs/heads/docs/**`), это тоже решение владельца.

### 4.3. Взаимодействие rulesets

| Actor | Push в `docs/x`, `impl/x` | Push в `feature/x` | Push в `develop` напрямую | Merge одобренного PR в `develop` | Изменение rulesets |
| --- | --- | --- | --- | --- | --- |
| Команда (A или B) | Разрешён | Отклонён (4.2 `creation`/`update`) | Отклонён (4.1 `pull_request` и 4.2 `update`) | Отклонён (4.2 `update`) | 403 (нет `administration`) |
| Владелец (`admin`) | Разрешён | Разрешён (bypass 4.2) | Отклонён (4.1, без bypass) | Разрешён при 1 одобрении не автором | Разрешён (аудит репозитория) |

Ограничение: при `required_approving_review_count = 1` владелец не сможет слить **собственный** PR без второго человека. Для PR команды это не мешает (одобряет владелец). Для собственных PR владельца потребуется второй ревьюер либо временное изменение ruleset владельцем — действие остаётся в журнале аудита.

### 4.4. Что rulesets не покрывают

- Изменение самих rulesets, секретов, Actions, коллабораторов — закрывается только отсутствием `administration` у actor команды (раздел 3).
- Содержимое push (запрет `.github/`, CLAUDE.md, CODEOWNERS по D-10 §2) — ветковые правила этого не проверяют; остаётся security preflight (TC-D10-01…03). Правило `file_path_restriction` доступно не на всех планах GitHub; при доступности — отдельное предложение.
- Одобрение PR владельцем остаётся ручным.

## 5. План проверки (после применения владельцем)

Ничего из этого раздела не выполнялось. Любая проверка, создающая или меняющая объекты GitHub (ветки, PR, ruleset, описание репозитория), выполняется только по отдельному разрешению владельца (раздел 7, п. 5). До выполнения все ожидания — NOT VERIFIED.

Принципы доказательства:

- **Пригодность схемы подтверждается положительными исходами**, а не только отказами: разрешённый push команды (TC-D10-06-03) и слияние PR владельцем (TC-D10-06-11) обязаны пройти. Схема, которая отклоняет всё, непригодна.
- **Слияние подтверждается только фактическим слиянием**: `merged = true` у PR и merge-коммит в целевой ветке. Закрытие PR без слияния проверку слияния не подтверждает.
- **Заголовок `X-Accepted-GitHub-Permissions` доказательством не считается** — ни прав токена, ни причины отказа. Права подтверждаются записью сервера о конфигурации (установка приложения или настройки PAT, раздел 5.2), причина отказа — классификацией ответа по разделу 5.2.1: подтверждённый отказ авторизации при позитивном контроле владельцем тем же валидным запросом и неизменности объекта. Ответ «не 2xx» сам по себе отказом авторизации не считается.
- **Негативные запросы — только к валидным, заранее согласованным объектам** (раздел 5.1) с валидным телом запроса: отказ на несуществующем объекте или некорректном теле (404/422) ничего не доказывает о правах.

#### 5.2.1. Классификация ответа на негативный запрос команды (TC-D10-06-02c)

Ответ на попытку команды относится ровно к одному классу. Заголовки ответа (`X-Accepted-GitHub-Permissions`, `X-RateLimit-*`, `Retry-After` и др.) могут только перевести результат в INCONCLUSIVE, но никогда не подтверждают отказ авторизации.

| Класс | Условия (все одновременно) | Итог для попытки |
| --- | --- | --- |
| **Подтверждённый отказ авторизации** | (а) ответ сформирован GitHub API, а не промежуточным узлом: запрос выполнен из окружения без перехватывающего прокси, согласованного с владельцем, либо журнал прокси показывает передачу запроса в GitHub и ответа без изменений; (б) статус 403 или 404 — 404 допустим только потому, что существование объекта подтверждено `GET` владельца в том же окне; (в) нет признаков ограничения частоты (см. INCONCLUSIVE); (г) учётные данные команды действительны в том же окне: контрольный запрос команды `GET /repos/{o}/{r}` → 200; (д) обе попытки команды дали одинаковый статус; (е) тот же запрос владельца в том же окне → 2xx | Засчитывается в PASS |
| **Разрешено** | Статус 2xx на попытку команды, **или** объект изменился по `GET` владельца — независимо от статуса | FAIL TC-D10-06-02c; схема непригодна |
| **INCONCLUSIVE** | Любое из: сетевая ошибка, таймаут, обрыв соединения; 5xx; 429; 403 с признаками ограничения частоты (сообщение об ограничении частоты, `Retry-After`, `X-RateLimit-Remaining: 0`); отказ или подмена ответа прокси; 401 (сбой аутентификации — о правах не говорит); 400, 409, 422 (запрос признан некорректным); 403/404 без выполнения условий (а), (г), (д) или (е); любой иной ответ или неустановленная причина | TC-D10-06-02c не пройдена; статус NOT VERIFIED; проверку можно повторить в новом окне |

Окно проверки — непрерывный интервал, в котором выполняются шаги (1)–(5) для одного запроса; рекомендуемая длительность — не более 30 минут. В протокол вносятся для каждой попытки: время, метод, путь, тело, статус, тело ответа (без токенов) и присвоенный класс с обоснованием.

### 5.4. Слияние: запрет для команды и успех для владельца

Выполняется на O-5 → O-1. Сливать в `develop` или `main` в рамках проверки не требуется: правила O-1 совпадают с правилами `develop` и `main` (TC-D10-06-04m).

| ID | Шаг | Ожидание (критерий PASS) |
| --- | --- | --- |
| TC-D10-06-08 | Команда открывает PR O-5; до одобрения `PUT /repos/{o}/{r}/pulls/{n}/merge` | Отказ; PR не слит (`merged = false`); SHA O-1 не изменился |
| TC-D10-06-09 | Команда отправляет одобрение своего PR (`POST …/reviews`, `event: APPROVE`) | Отказ (автор не может одобрить свой PR); у PR нет одобрения от команды |

### 5.5. Порядок, откат и критерий закрытия

Порядок: O-1…O-3 (владелец) → 01, 02 → 03 (создаёт O-4) → 04, 04m, 05 → 08 (создаёт O-5) → 09 → 10 → 11 → 06, 07 → удаление O-1, O-2, O-4, восстановление `include` 4.1 и описания (O-3) → TC-D10-05 (повтор: `GET` обоих ruleset совпадает с проектом раздела 4). Протокол: запросы и ответы (без токенов), SHA веток до и после, выдержки `rule-suites`.

TC-D10-06 закрывается при PASS всех обязательных проверок: 01 (a или b), 02 (a или b), 02c, **03**, 04, 04m, 05, 08, 09, 10, **11** и TC-D10-05. Результаты 06 и 07 фиксируются без влияния на закрытие. Любой обязательный FAIL — схема непригодна, раздел 4 пересматривается. INCONCLUSIVE по обязательной проверке (в том числе по классификации 5.2.1) не является ни PASS, ни FAIL: TC-D10-06 остаётся **NOT VERIFIED** до повторной проверки с однозначным исходом. До выполнения статус — **NOT VERIFIED**.

## 6. Риски и побочные эффекты

| Риск | Последствие | Смягчение |

## 7. Решения, требуемые от владельца

1. Вариант идентичности команды: A (GitHub App) или B (машинная учётная запись + fine-grained PAT).
2. Пространство имён команды в 4.2: `docs/**` и `impl/**`, либо уже (`docs/arch-0001`, конкретные `impl/*`), либо шире (`fix/**`).
3. `required_approving_review_count = 1`, `dismiss_stale_reviews_on_push`, `require_last_push_approval`, единственный метод `merge` — принять или изменить.
4. Защищать ли ветки команды от force push и удаления (расширение `non_fast_forward`/`deletion` на `docs/**`, `impl/**`).
5. Разрешение на проверки раздела 5: создание тестовых объектов O-1…O-5, временное добавление O-1 в `include` ruleset 4.1, позитивный контроль 02c (временное изменение O-2 и описания репозитория с возвратом), слияние PR O-5 в O-1.

До этих решений команда ничего не меняет в настройках репозитория.
