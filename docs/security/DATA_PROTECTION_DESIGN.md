## 1. Границы

| Граница | Правило |
| --- | --- |
| Сбор | Агент и шлюзы собирают только события по каналам и операциям, входящим в область опубликованной политики. Сплошная запись файловой активности не ведётся (кандидат FID/DLP-ENDPOINT-001 требует согласования, RECON-0001 §6) |
| Передача | Уровень `METADATA` по умолчанию; `MASKED_MATCH` и `FULL_EVIDENCE` — только по явному действию правила (ADR-0017) |
| Хранение | Метаданные — PostgreSQL; evidence — отдельное хранилище с шифрованием на уровне приложения |
| Доступ | Только через API сервера; права с областью по подразделению; каждый просмотр, экспорт и удаление аудируется |
| Удаление | По срокам хранения с учётом legal hold; удаление evidence — crypto-shredding |

До решения по Q-04 правомерность сбора `FULL_EVIDENCE` не утверждается. В MVP возможность сбора полного содержимого выключена на уровне платформы.

### 2.1. Минимизация путей файлов (AR-07)

Полный путь файла не передаётся в METADATA по умолчанию. Уровень пути задаётся в действии правила (`path_level`) и наследует ограничения D-07:

| `path_level` | Что передаётся | По умолчанию |
| --- | --- | --- |
| `CLASS` | `path_class`, `extension` | — |
| `PSEUDONYMIZED` | `CLASS` + `path_hmac` | **Да** (Proposed) |
| `FULL` | `PSEUDONYMIZED` + `path_full` (зашифрован) | Только по явному действию правила; требует права `incident.view_path` для просмотра |

- Имя файла входит в `path_full` и по умолчанию тоже не передаётся.
- Расследователь с известным путём может проверить совпадение: сервер вычисляет HMAC введённого пути и сравнивает. Операция требует права `incident.view_path` и записывается в аудит. Обратного преобразования HMAC в путь нет.
- Ротация ключа HMAC разрывает связь новых и старых псевдонимов; ротация выполняется по периодам и записывается в аудит.

**Область и размещение ключа HMAC — Pending, решение владельца:**

| Вариант | Где вычисляется HMAC | Связываемость | Риск |
| --- | --- | --- | --- |
| A. Ключ развёртывания на всех агентах | Агент | Один путь на разных устройствах даёт один псевдоним | Ключ извлекается локальным администратором любого устройства; перебор типичных путей раскрывает псевдонимы всего развёртывания |
| B. Ключ подразделения (tenant) на агентах подразделения | Агент | Связываемость внутри подразделения | Компрометация ключа затрагивает подразделение |
| C. Ключ на агенте (per-agent) | Агент | Связываемость только внутри устройства | Компрометация затрагивает одно устройство; корреляция между устройствами невозможна |
| D. Ключ только на сервере | Сервер: агент передаёт путь, зашифрованный открытым ключом сервера; сервер вычисляет HMAC и сразу отбрасывает путь, если уровень не `FULL` | Задаётся областью серверного ключа | Полный путь кратковременно доступен серверу; на endpoint ключа нет |

- Пути низкоэнтропийны, поэтому HMAC с известным ключом раскрывается перебором словаря типичных путей. Ключ не должен быть доступен тем, от кого скрываются пути.
- Каждый псевдоним хранит идентификатор версии ключа. Ротация по периоду (Proposed: квартал). Старые версии уничтожаются после срока хранения событий; после этого старые псевдонимы несвязываемы.
- Рекомендация команды — D или C; решение — владелец продукта с учётом Q-04.
- Значение `path_level` по умолчанию и допустимость `FULL` — Pending: утверждает владелец продукта с учётом Q-04.

## 3. Маскирование

- Маскирование выполняется в `sentinel-core` до того, как фрагмент покидает процесс инспекции (DLP-DETECTION-006).
- Правило маскирования задаётся для типа детектора; для пользовательских regex без правила по умолчанию маскируется всё, кроме длины и класса символов.
- Маскированный фрагмент короткого значения (например, 4–6 цифр) может быть восстановлен перебором. Для таких детекторов фрагменты не передаются.

## 4. Хранилище evidence и ключи

```text
KEK (KMS/HSM или локальный ключ, защищённый оператором)
  └─ шифрует DEK (отдельный ключ на объект evidence)
        └─ AES-256-GCM: объект evidence + метаданные целостности (SHA-256 исходного объекта)
```

- DEK уникален для каждого объекта; хранится только в зашифрованном виде рядом с метаданными в PostgreSQL.
- DEK шифруются ключом периода KEK_P (§7.1). KEK не хранится в той же БД и не входит в её резервные копии.
- Интеграция с KMS/HSM через PKCS#11 или KMIP — архитектурная возможность; конкретный продукт и протокол — Pending (связано с Q-07 и кандидатом U-05).
- Целостность: хеш исходного объекта фиксируется при создании; при каждом чтении проверяется хеш и тег GCM.
- Выбор хранилища (локальная ФС или S3-совместимое) — Pending, C-05.

Права (роли формируются из прав; модель ролей с разделением обязанностей — кандидат U-03, на согласовании):

| Право | Что разрешает | Дополнительные условия |
| --- | --- | --- |
| `incident.view` | Метаданные инцидентов в области | — |
| `incident.view_masked` | Маскированные фрагменты | Аудит каждого просмотра |
| `incident.view_path` | Полный путь файла; проверка пути по HMAC | Обоснование; аудит каждого просмотра и проверки |
| `evidence.view` | Полное evidence | Привязка к инциденту, обоснование, повторная проверка MFA, аудит |
| `evidence.export` | Экспорт одного инцидента | Аудит; манифест хешей (кандидат FID/DLP-INCIDENT-009) |
| `evidence.export_bulk` | Массовый экспорт: больше 10 инцидентов или любой экспорт `FULL_EVIDENCE` (Proposed) | Двойной контроль: второе лицо с тем же правом подтверждает; самоподтверждение запрещено |
| `evidence.delete` | Досрочное удаление | Двойной контроль; запрещено при legal hold |

- Проверка прав выполняется на сервере для каждого запроса и для каждого объекта. Отказ возвращается без раскрытия существования объекта вне области.
- Консоль работает только через публичный API; у неё нет учётных данных БД. Это исключает обход авторизации через прямой доступ к данным.

Значения утверждаются после ответа на Q-04.

- Legal hold приостанавливает удаление для инцидента и связанных объектов.

- Физическое затирание на SSD и в объектном хранилище не гарантируется и не заявляется. Удаление обеспечивается криптографически (§7).

## 7. Crypto-shredding и резервные копии (AR-08)

### 7.1. Иерархия ключей

```text
KEK_P (ключ периода P, например календарный месяц; в KMS/HSM или защищённом хранилище ключей)
  └─ шифрует DEK_i каждого объекта evidence, созданного в периоде P
        └─ AES-256-GCM: объект evidence
```

Зашифрованный DEK хранится в PostgreSQL и поэтому попадает в резервные копии БД. KEK в резервные копии БД не входит.

### 7.2. Что происходит при удалении

| Шаг | Действие | Когда объект становится нерасшифровываемым |
| --- | --- | --- |
| 1 | Досрочное удаление объекта: удалить зашифрованный DEK и объект в рабочей системе; добавить запись в журнал удалений (`deletion_tombstone`) | В рабочей системе — сразу |
| 2 | Резервные копии, сделанные до удаления, ещё содержат зашифрованный DEK; пока существует KEK_P, объект восстановим из копии | После истечения срока хранения всех копий, содержащих DEK |
| 3 | Уничтожение KEK_P после окончания срока хранения всех объектов периода и всех копий | Для всего периода — сразу, во всех копиях |

**Граница crypto-shredding (SR3-05).**

**Область критерия.** Критерий ниже относится только к шифротексту evidence в хранилище evidence и к его ключевому материалу. Открытые копии содержимого crypto-shredding не удаляет: экспорт evidence (`evidence.export`, §5), фрагменты в метаданных инцидента, данные, переданные в SIEM, аварийные дампы (§9). Они учитываются и удаляются по собственным срокам и процедурам. Пока такая копия существует, удаление объекта не завершено, даже если `T_eff` наступил.

*Путь восстановления* — любое предусмотренное или фактически существующее место, где можно соединить материал, необходимый для расшифровки объекта:
- рабочая БД и её реплики;
- резервные копии БД и хранилища объектов;
- KMS/HSM и резервные копии HSM;
- экспорт ключей, эскроу ключей;
- ключ удержания `KEK_HOLD` для объектов под legal hold.

Для расшифровки объекта нужна **полная комбинация**: шифротекст объекта, его DEK, обёрнутый некоторым ключом `K`, и сам ключ `K`. `K` — это KEK_P, `KEK_HOLD` или ключ эскроу.

**Критерий (для шифротекста evidence).** Объект невосстановим из хранилища evidence тогда и только тогда, когда ни в одном пути восстановления — и ни в каком их сочетании, доступном одному лицу или группе лиц, — нельзя одновременно получить шифротекст, обёрнутый DEK и соответствующий ему ключ `K`.

Следствие: достаточно, чтобы во **всех** копиях исчезла **хотя бы одна** часть комбинации. Например, все копии обёрнутого DEK — или все копии ключа `K`. Одновременное уничтожение и DEK, и KEK не требуется. Формулировка ревизии 3 «одновременно недоступны DEK и KEK_P» была ошибочной: она требовала больше, чем нужно, и противоречила формуле ниже.

**Срок полного вступления удаления в силу.** Обозначения:
- `T_obj` — момент, когда уничтожены все копии шифротекста. Физическое затирание носителей не гарантируется (§6), поэтому, пока уничтожение не подтверждено, `T_obj = ∞`;
- `T_dek(K)` — момент, когда уничтожены все копии DEK, обёрнутого ключом `K`;
- `T_key(K)` — момент, когда уничтожены все копии ключа `K`, включая резервные копии HSM и эскроу.

```text
T_eff = min( T_obj,  max по всем K, которыми обёрнут DEK [ min( T_dek(K), T_key(K) ) ] )
```

В типичном случае без legal hold и эскроу DEK обёрнут только KEK_P. Тогда `T_eff = min(T_obj, T_dek(KEK_P), T_key(KEK_P))`, где:
- `T_dek(KEK_P)` — окончание срока хранения последней копии БД, содержащей обёрнутый DEK;
- `T_key(KEK_P)` — уничтожение KEK_P во всех копиях.

До `T_eff` удалённое evidence восстановимо лицом, получившим недостающие части комбинации. Это остаточный риск R-21.

**Сохраняемые ограничения:**
- **Резервные копии.** Пока существует копия БД с обёрнутым DEK и любая копия соответствующего ключа, объект восстановим. Журнал удалений повторно применяется после каждого восстановления (§7.4), но не делает удаление необратимым для лица, у которого есть копия и ключ вне штатной процедуры восстановления.
- **Эскроу и резервирование ключей.** Каждая копия ключа учитывается в реестре ключей (§7.3). Неучтённая копия любого ключа `K` делает расчёт `T_eff` недостоверным.
- **Legal hold.** DEK объекта под удержанием перешифровывается ключом `KEK_HOLD` до уничтожения KEK_P (§7.3). Пока удержание действует, `T_key(KEK_HOLD)` не наступает, и объект намеренно остаётся восстановимым. Снятие удержания — двойной контроль. При снятии удаляется обёртка DEK ключом `KEK_HOLD`. Ключ `KEK_HOLD` общий для удерживаемых объектов и не уничтожается, поэтому после снятия удержания `T_eff` определяется сроком хранения копий БД с этой обёрткой — `T_dek(KEK_HOLD)`. Без удаления обёртки объект остался бы восстановимым бессрочно (TC-D07-05).
- **Независимый аудит удаления.** Уничтожение ключей и достижение `T_eff` подтверждаются:
  - записями аудита с внешней контрольной точкой (§8);
  - проверкой реестра ключей лицом, не выполнявшим уничтожение (§7.3).
- **Досрочное удаление одного объекта** не может стать необратимым раньше `T_eff`. Необратимое досрочное удаление отдельного объекта требует отдельного ключа на объект или инцидент вне резервируемой БД. Это отдельное решение (Pending).
- Уничтожение KEK_P необратимо удаляет все объекты периода, не перешифрованные ключом `KEK_HOLD`. Поэтому длина периода — компромисс между гранулярностью удаления и числом ключей.

### 7.3. Уничтожение ключевого материала

- KEK_P уничтожается в KMS/HSM двойным контролем; операция записывается в аудит и во внешнюю контрольную точку (§8).
- Резервные копии самого ключа (резервирование HSM, экспорт ключа) учитываются в реестре ключей и уничтожаются той же процедурой. Существование неучтённой копии KEK делает crypto-shredding недействительным — это проверяется аудитом реестра ключей.
- Если объект периода P находится под legal hold, его DEK заранее перешифровывается ключом удержания `KEK_HOLD`; только после этого KEK_P уничтожается.

### 7.4. Восстановление из резервной копии

- Журнал удалений `deletion_tombstone` хранится отдельно от резервируемой БД (во внешней системе аудита или в отдельном хранилище с собственным сроком хранения) и **повторно применяется после каждого восстановления**. Это исключает возврат удалённого evidence при восстановлении копии, сделанной до удаления.
- Отчёт о восстановлении содержит результат повторного применения журнала (TC-D07-12).
- Доступ к копиям — отдельная роль; восстановление — двойной контроль и аудит.
- Резервные копии шифруются; ключи шифрования копий хранятся отдельно от копий.

## 8. Аудит и его целостность

- Аудируются: просмотр, экспорт и удаление evidence; изменение прав, политик, исключений, сроков хранения; break-glass; операции с ключами.
- Каждая запись содержит хеш предыдущей.
- Внешнее закрепление: периодически (Proposed: каждые 15 минут и при каждом критическом действии) подписанная контрольная точка — номер, хеш головы цепочки, время — отправляется во внешнюю систему: SIEM или WORM-хранилище организации (DLP-CORE-015). Без внешнего закрепления администратор БД с доступом к ключу теоретически может пересчитать цепочку.
- Отклонять ли критическое действие при невозможности записать аудит — кандидат U-04, на согласовании.

## 9. Логи, трассировки, аварийные дампы

- В структурированных логах — только поля из явного списка разрешённых; поля с содержимым, фрагментами и путями проходят фильтр.
- Атрибуты трассировок — тот же список.
- Аварийные дампы процессов, обрабатывающих содержимое, по умолчанию выключены или ограничены минимальным дампом без памяти кучи. Включение полного дампа — диагностическая операция с аудитом и сроком.
- Проверка — тест с маркером: уникальная строка в тестовом документе не должна обнаруживаться в логах, трассировках, дампах, БД и хранилище, кроме разрешённого уровня (TC-D07-07).

## 10. Проверки

См. docs/TEST_STRATEGY.md, раздел D-07 (TC-D07-01…12): несанкционированный доступ, экспорт инсайдером, подмена evidence, утечка через резервную копию, истечение срока хранения, скомпрометированная учётная запись аналитика, утечка через логи, минимизация путей, уничтожение KEK периода, восстановление с повторным применением журнала удалений.
