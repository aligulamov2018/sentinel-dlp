## 3. Кодировки

### 3.1. Поддерживаемые кодировки (P-01)

**Профиль §0.1 (PRF-1, утверждено 2026-11-16): вариант B** — UTF-8 (с BOM и без), UTF-16LE и UTF-16BE с BOM. Windows-1251 не выбирается: объект, F которого не проходит CAND как UTF-8, получает E-05. Правила Windows-1251 (таблица Unicode.org `CP1251.TXT`, байт `0x98` не определён; E-16) сохранены в тексте как отложенные и в профиле не действуют.

**Остаточный риск E16 (PRF-4, принят только для профиля §0.1 в `InspectionOnly`).** Объект в Windows-1251 без BOM, вся прочитанная часть которого декодируется как UTF-8 без ошибок и не упирается в лимит, выбирается как UTF-8: COMPLETE, без причин; детектор работает по неверному тексту и может пропустить совпадение (CE-21c). Объект с двумя соседними буквами А–я (байты C0–FF) внутри F получает E-05. За F такие буквы дают E-13 (`PARSE_ERROR`), если декодер доходит до них раньше лимита; иначе причина — `RESOURCE_EXHAUSTED`. Для `EnforcementReady` нужно отдельное решение.

**Исправлено (E1-AR1-04).** UTF-16 без BOM **не выбирается как кодировка**. Такие байты могут быть приняты в другой кодировке или отклонены — это остаточный риск. Пример: байты `42 41` — это U+4142 в UTF-16LE без BOM и одновременно корректный UTF-8 `BA`. Алгоритм выберет UTF-8 (CE-6).

### 3.2. Порядок выбора

Начальный фрагмент F — первые `n_F = min(L-3, len)` байт объекта. Ограничение `L-3 ≤ L-1` задаёт L-0.

| Шаг | Условие | Решение |
| --- | --- | --- |
| ENC-0 | `len = 0` | Текст `""`, класс `txt`, UTF-8; E-01 |
| ENC-1 | Сигнатура SIG-1…SIG-4 | По таблице 2.1 |
| ENC-2…4 | `EF BB BF` / `FF FE` / `FE FF` | Кандидат UTF-8 / UTF-16LE / UTF-16BE; BOM не входит в текст |
| ENC-5 | Нет BOM; F — корректный UTF-8 (с учётом FRAG-1) | Кандидат UTF-8 |
| ENC-6 | **Исключён из профиля §0.1** (PRF-1: L-7 = `false`). Вне профиля: нет BOM; F не UTF-8; Windows-1251 разрешена | Вне профиля: кандидат Windows-1251 |
| ENC-7 | Иначе | `NotInspected(UNSUPPORTED_FORMAT)`, `unknown` |

Условия кандидата CAND проверяются только на F, без чтения за его пределами (P-03):
1. Декодирование без ошибок. Для Windows-1251 (вне профиля) ошибка — байт `0x98`. Неполная последовательность в конце F, являющаяся корректным началом, — не ошибка: при обрыве F (FRAG-1a) и при конце объекта внутри F (FRAG-1b). **(уточнено, v0.6)** Для UTF-16 корректность начала определяется по критерию UTF-16 из FRAG-1a — с учётом порядка байтов и состояния пары суррогатов; недопустимый хвост — ошибка по этому пункту.
2. Нет байта `0x00` — для UTF-8 и Windows-1251 (A). Для UTF-16 байты `0x00` допустимы, U+0000 учитывается в п. 3 (A).
3. Доля управляющих символов **ниже** порога (CTL-1, A).

Отклонённый по п. 1 кандидат ENC-5 → ENC-7 в профиле §0.1 (вне профиля — ENC-6). Отклонённый кандидат с BOM → ENC-7.

### 3.3. Управляющие символы (исправлено, E1-AR1-04; P-05)

| ID | Правило | Статус |
| --- | --- | --- |
| CTL-1 | Управляющие: U+0000…U+001F, **кроме U+0009, U+000A, U+000D**; U+007F; U+0080…U+009F. **U+000C (form feed) — управляющий.** Кандидат принят, если `control × 1000 < total × T` (строго), где `T = L-4` в промилле и `total > 0` | Перечень исключений — A (SENTINEL_CORE_DESIGN.md §4.3: «кроме перевода строки, табуляции и возврата каретки»). «Ниже порога» — A. Включение C1 и U+007F — U (по общему смыслу «управляющих»). Значение T — P-08 |
| CTL-2 | То же условие на всём содержимом по итоговым счётчикам (PG-1) | A |

В версии 0.1 U+000C исключался из управляющих, а равенство порогу допускалось — это изменение принятого правила. Оно отозвано. Желающим его вернуть — отдельное предложение P-05 (альтернатива, не рекомендуется).

| FRAG-1a | **Без дочитывания (P-03).** Если F обрывается (`n_F = L-3 < len`) неполной последовательностью, которая является корректным началом допустимой последовательности (UTF-8: ведущий байт и допустимые продолжения по Unicode, табл. 3-7; UTF-16 — см. **критерий UTF-16** ниже), — это не ошибка CAND. Незавершённый хвост — корректное начало, только если его можно дополнить до допустимого UTF-16:<br>– один байт новой единицы: в UTF-16BE это старший байт, допустим любой, **кроме `DC…DF`** (он начинает непарный младший суррогат); в UTF-16LE это младший байт, допустим любой;<br>– полная единица старшего суррогата;<br>– старший суррогат и один байт следующей единицы, которая обязана быть младшим суррогатом: в UTF-16BE байт **только `DC…DF`**; в UTF-16LE — любой.<br>Иной хвост уже недопустим: это ошибка декодирования по п. 1 CAND, кандидат отклоняется (с BOM → ENC-7, E-05). Эталоны: CE-20k (допустимый, F обрывается), CE-20l, CE-20m (недопустимые) | N |
| FRAG-1b | **(новое, PRF-3: P-03a, F-b)** Если объект целиком лежит в F (`n_F = len`) и кончается такой же корректной, но незавершённой последовательностью, — это тоже не ошибка CAND. После выбора кодировки хвост обрабатывается по E-14 (UTF-8) или E-15b (UTF-16): U+FFFD, `PARSE_ERROR` (CE-20a…e, CE-20g, CE-20h). Критерий допустимости — тот же, что в FRAG-1a, включая критерий UTF-16. Недопустимый хвост (не корректное начало) по-прежнему отклоняет кандидата (CE-20f, CE-21b; UTF-16BE — CE-20i, CE-20j) | N (уточнение принятого SENTINEL_CORE_DESIGN.md §4.3) |
| FRAG-2 | Объект кончается неполной последовательностью → E-14 (UTF-8) или E-15b (UTF-16) | U |
| FRAG-3 | Независимость от размеров блоков и коротких чтений — в области P-16 (§4.4) | U |
| FRAG-4 | Обрезка по L-1, L-2 или бюджету — по границе последнего полного скалярного значения. Неполная последовательность на месте обрезки не даёт `PARSE_ERROR` | N (часть P-06) |

### 4.2. Операционная семантика бюджета (P-06; исправлено, E1-AR1-01)

**Рекомендуемый вариант P-06-A: единица извлечения — байт, фактически возвращённый `ContentSource::read_at`.** Основание: SENTINEL_CORE_DESIGN.md §10.1 называет единицами работы прочитанные байты, распакованные байты, узлы XML, объекты PDF и **символы для детекторов**. Символы списываются на этапе `analyze` (Э-2), а не при извлечении. Работа декодирования линейна по числу прочитанных байт, поэтому вывод отдельно не списывается. Он ограничен лимитом памяти L-2, а не бюджетом. Это определение единиц извлечения, а не отказ учитывать выполненную работу: **каждый** физически прочитанный байт — фрагмент, опережающие блоки, хвост после остановки — списывается.

| ID | Правило |
| --- | --- |
| B-1 | `bytes_read` — сумма байт, возвращённых всеми вызовами `read_at`. Списание `charged = bytes_read` происходит в момент возврата. Других единиц у извлечения нет |
| B-2 | **Ограничение запросов (резервирование).** Каждый запрос `read_at` запрашивает не больше `q = min(K-1, L-1 − bytes_read, budget − bytes_read, len − bytes_read)`. Если `q = 0`, чтение прекращается. Поэтому `bytes_read ≤ min(L-1, budget, len)` всегда: чтения сверх лимита и бюджета нет |
| B-3 | **Предварительная проверка и фаза C.** Решению CAND нужно ровно `n_F` байт. Если `budget < n_F`, ничего не читается, результат — E-24 (`bytes_read = 0`). Иначе F читается запросами `q_C = min(K-1, n_F − bytes_read)` (короткие чтения допустимы) и удерживается в `TextProbe` (P-07). Перед каждым запросом проверяется дедлайн (B-9). После фазы C `bytes_read = n_F` всегда, независимо от того, сколько из F затем войдёт в текст |
| B-4 | Повторные чтения запрещены: F передаётся в `extract` через `TextProbe`, а не перечитывается. Если реализация прочитает байт повторно, он будет списан повторно (B-1). Проверка E1-T-14: `bytes_read` равно ожидаемому |
| B-5 | **Терминальные события и `stop_cause` (исправлено, E1-AR2-01).** `stop_cause` — событие, на котором остановился **декодер** по порядку B-11, а не состояние источника. Значения: `Complete` — декодер обработал все `len` байт и каждый скаляр добавлен; `OutputLimit` — следующий декодированный скаляр не помещается в L-2 (E-22); `InputLimit` / `Budget` — декодеру нужен следующий байт, а запрос по B-2 даёт `q = 0` из-за L-1 / бюджета (при одновременном исчерпании — `InputLimit`); `Deadline`, `Cancel`, `ReadError`, `UnexpectedEof`. События взаимоисключающи по построению: каждое обнаруживается в одной точке B-11. **Физический конец источника** — отдельный флаг `source_exhausted = (bytes_read = len)`. Он не является причиной остановки и не скрывает `OutputLimit`: `stop_cause = OutputLimit` при `source_exhausted = true` допустим (CE-11…CE-13, CE-16). Значение `Eof` версии 0.2 упразднено |
| B-6 | **Граница `bytes_read` при `OutputLimit` (исправлено, E1-AR2-01).** Выведена из порядка B-11. Каждый физически прочитанный байт списан (B-1). Декодер просмотрел не дальше `w ≤ bytes_consumed + 4`: самый длинный скаляр или максимальная недопустимая подпоследовательность вместе с байтом, завершившим её распознавание. Новое чтение выдаётся только при исчерпанном буфере, то есть с позиции не дальше `w − 1`, и запрашивает не больше K-1 байт. F прочитан целиком в фазе C. Отсюда `max(n_F, bytes_consumed + 1) ≤ bytes_read ≤ min(max(n_F, bytes_consumed + 3 + K-1), L-1, budget, len)`. Короткие чтения только уменьшают `bytes_read` в этих границах. Формула версии 0.2 (`≤ bytes_consumed + K-1 + 3`) не учитывала F и отвергается контрпримером CE-10 (`16 ≤ 8` ложно) |
| B-7 | Частичный текст **сохраняется** при `InputLimit`, `Budget`, `OutputLimit`, `Deadline` после CAND. **Отбрасывается** при `Cancel`, `ReadError`, `UnexpectedEof` |
| B-8 | Паника — дефект; в Э-1 нет `Engine`, перехват не реализуется. Отсутствие паник проверяет фаззинг |
| B-9 | Дедлайн проверяется перед каждым запросом `read_at` (P-16) |
| B-10 | **Учёт событий по добавленным скалярам.** `decode_replacements`, `nul_bytes_after_fragment`, `control_chars`, `scalars_written`, `text_bytes` и причины `PARSE_ERROR`, `UNSUPPORTED_FORMAT` от E-13…E-18 считаются только по скалярам, добавленным в текст. Скаляр, не принятый из-за L-2, не учитывается: недопустимая последовательность за точкой остановки не даёт `PARSE_ERROR`; часть объекта после остановки покрыта причиной `RESOURCE_EXHAUSTED` (CE-16) |
| B-11 | **Порядок обработки (исправлено, E1-AR2-01).** D-0: фаза C (B-3), CAND по F. D-1: декодер берёт байты сначала из F (после BOM), затем из буфера чтения — «декодировать до чтения». D-2: каждый полностью декодированный скаляр, включая U+FFFD, проверяется по L-2: `text_bytes + len_utf8(скаляр) > L-2` → `OutputLimit`, скаляр не добавляется, `bytes_consumed` не меняется; иначе он добавляется, и `bytes_consumed` становится концом его байт. D-3: когда декодеру нужен байт с позиции `bytes_read`: если `bytes_read = len` — конец входа (незавершённая последовательность → E-14 через D-2, затем `Complete`); иначе проверяется дедлайн (B-9) и вычисляется q (B-2); `q = 0` → `InputLimit` или `Budget` (незавершённая последовательность отбрасывается по FRAG-4); иначе выдаётся один запрос `read_at`. D-4: запрос не выдаётся, пока в буфере есть необработанные байты. D-5: после остановки с сохранением текста — CTL-2 по добавленным скалярам и сегментация CSV по тексту |

**Альтернатива P-06-B: двухкомпонентный бюджет** (байты чтения и скалярные значения вывода, каждый со своим пределом).
- Сохраняет учёт вывода.
- Требует от хоста двух чисел.
- Удваивает правила остановки.
- Бюджет вывода дублирует L-2 в других единицах.

Не рекомендуется. Исходы контрпримеров при этом варианте даны в §10.

### 4.4. Область независимости от блоков и тестовый дедлайн (P-16)

| Случай `stop_cause` | Независимы от K-1 и коротких чтений | Не обещается |
| --- | --- | --- |
| `Complete`, `InputLimit`, `Budget` | Всё: текст, сегменты, причины, покрытие, все счётчики, включая `bytes_read` (равен `len`, L-1 или бюджету) и `source_exhausted` | — |
| `OutputLimit` | Текст, сегменты, причины, покрытие, `stop_cause`, `bytes_consumed`, `scalars_written`, `text_bytes`, `decode_replacements`, `nul_bytes_after_fragment`, `control_chars` | `bytes_read` (границы B-6) и `source_exhausted`: для одного входа большой блок может достичь физического конца, а малый — нет (CE-11, CE-12) |
| `Deadline`, `Cancel`, `ReadError`, `UnexpectedEof`, смена содержимого источника во время чтения | — | Всё |

Одновременные условия разрешаются по B-5 и B-11. Достигнутый физический конец источника вместе с отказом добавить скаляр — это `OutputLimit`, а не `Complete`. `Complete` требует, чтобы все `len` байт были обработаны и каждый скаляр добавлен. Если L-2 ровно заполнен последним скаляром перед концом входа, это `Complete` (CE-14).

Детерминированный тестовый токен `TestDeadline::after_bytes(X)` срабатывает при первой проверке (B-9), когда `bytes_read ≥ X`. Ожидаемая позиция останова при блоке размера B и без коротких чтений вычисляется по правилу B-2: первая граница запроса ≥ X. Тест сверяет её для каждого B и не требует равенства между разными B.

### 4.5. Память (исправлено; P-14)

Удерживаемые буферы:
- ёмкость текста ≤ L-2 — рост блоками, ёмкость не выше L-2;
- ёмкость вектора сегментов ≤ L-5;
- F ≤ L-3 — освобождается после перехода к декодированию;
- буфер блока ≤ K-1;
- перенос декодера ≤ 4 байт.

«Константа» — структуры фиксированного размера, суммарно не более 4 КиБ. Других выделений, растущих со входом, нет.

Проектная оценка пика — ≤ L-2 + L-3 + K-1 + L-5 × размер сегмента + 4 КиБ. Размер сегмента фиксируется в реализации и измеряется тестом через `size_of`.

Метод измерения — P-14 (утверждён M-1; ограничение оценки — KNOWN_ISSUES.md KI-14):
- **M-1 (рекомендуется):** проверка ёмкостей (`capacity()`) после работы и в точках роста, плюс пик RSS процесса на Linux (`/proc/self/status`, `VmHWM`) в отдельном тестовом процессе; только std, без `unsafe`;
- **M-2:** счётный аллокатор в отдельном тестовом crate вне продукта с разрешённым только там `unsafe`. Это исключение из `forbid(unsafe_code)` для тестовой оснастки, требует отдельного решения. Запрет в продукте не снимается.

## 5. CSV (P-10; исправлено, E1-AR1-03)

| ID | Правило |
| --- | --- |
| CSV-1 | Выбор TXT или CSV — только для принятого текста, только по декодированному F. На покрытие не влияет |
| CSV-2 | Разделители `,` `;` `\t` |
| CSV-3 | Кавычка `"`, экранирование `""`; кавычка распознаётся только в начале поля; разделители и переводы строк внутри кавычек допустимы; конец записи вне кавычек — CRLF, LF или CR |
| CSV-4 | Выборка — до 50 записей, целиком лежащих в F, не меньше 2. Разделитель подходит при одинаковом числе полей k ≥ 2 во всех записях выборки и без ошибок кавычек. Выбирается наибольший k, при равенстве — порядок CSV-2. Иначе TXT. Расширение не учитывается |
| CSV-5 | **Представление.** `ExtractedContent.text` — исходный декодированный текст без изменений. Сегмент ячейки — `Cell { row, col, raw_range, quoted, has_escaped_quotes }`, где `raw_range` — диапазон внутри окружающих кавычек. Логическое значение (с `""` → `"`) в Э-1 **не** материализуется. Контракт даёт чистую функцию `csv_unescape(raw)`; кто и когда её вызывает, определяет потребитель (Э-2) |
| CSV-6 | Сегментация — по всему тексту выбранным разделителем; записи с другим числом полей допустимы |
| CSV-7 | Незакрытая кавычка до конца текста: остаток — сегмент `Tail { from_row, from_col, raw_range }`; `segmentation = Degraded { cause: UnterminatedQuote, from_byte }` |
| CSV-8 | **Лимит L-5 включает хвост.** Когда создано L-5 − 1 сегментов и текст не кончился, остаток — один сегмент `Tail`, `segmentation = Degraded { cause: SegmentLimit, from_byte }`. Всего сегментов ≤ L-5 |
| CSV-9 | TXT — один сегмент на весь текст, `segmentation = Complete` |
| CSV-10 | `text_coverage` и причины от сегментации не зависят: весь текст доступен |

**Отозвано (E1-AR1-03).** Утверждение версии 0.1 «лишние, но не пропущенные совпадения» неверно. Детектор, сопоставляющий значение ячейки целиком, на сегменте хвоста `SECRET,x\n` совпадения `SECRET` не найдёт (CE-5).

**Контракт потребителя сегментов** — предложение P-11, требование к Э-2:
- **P-11-A (рекомендуется).** В v0.1 детекторы работают только по тексту. Сегменты используются для расположения находок и объяснения, но не для сопоставления. Бандл с детектором, привязанным к ячейке, отклоняется при загрузке, как score-пороги в KI-08. Тогда деградация сегментации не меняет результатов детекторов (проверка E1-T-29 в Э-2).
- **P-11-B.** Детекторы по ячейкам разрешены. Тогда `analyze` обязан считать применение такого детектора неполным при `segmentation = Degraded`: его атомы на деградированной части — UNKNOWN, а не FALSE. Нужна причина неполноты — какая, отдельное решение. `text_coverage` при этом не меняется: текст извлечён полностью.

### 9.3. Трассы чтения для эталонов `OutputLimit` (новое, E1-AR3-01)

Конфигурация чтения задаётся парой (K-1, s):
- s — расписание коротких чтений: каждый вызов `read_at` возвращает `min(q, s)` байт;
- без коротких чтений — `s = ∞`.

Эффективный шаг `c = min(K-1, s)`. По B-2 и B-11 D-3–D-4 после фазы C запросы выдаются только при исчерпанном буфере, поэтому позиция чтения растёт шагами c от `n_F` до первого значения, покрывающего нужный декодеру байт, но не дальше `min(L-1, budget, len)`. Эталоны проверяются **для каждой конфигурации отдельно**, а не как множество возможных значений.

| Эталон | Нужный байт после F | `bytes_read` | c = 1 | c = 2 | c = 3 | c ≥ 4 |
| --- | --- | --- | --- | --- | --- | --- |
| CE-11 | `e` (смещение 4) | `min(6, 4 + c)` | 5 / false | 6 / true | 6 / true | 6 / true |
| CE-12 | конец `€` (смещение 5) | `min(7, 3 + c · ⌈3 / c⌉)` | 6 / false | 7 / true | 6 / false | 7 / true |
| CE-10, CE-15u | внутри F | `n_F` | 16 / false; 6 / false | то же | то же | то же |
| CE-13, CE-16, CE-17a, CE-18c | до конца источника | `len` | 8; 3; 5; 5 — true | то же | то же | то же |

В модели проверены K-1 ∈ {1, 2, 3, 4, 7, 65 536} × s ∈ {∞, 1, 2}.
