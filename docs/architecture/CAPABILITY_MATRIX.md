## 1. Статусы

| Статус | Значение |
| --- | --- |
| `BLOCK_CAPABLE` | Механизм платформы позволяет синхронно предотвратить операцию до её завершения |
| `MONITOR_ONLY` | Возможны только обнаружение и регистрация, без предотвращения |
| `SUPPORTED` | Канал поддерживается в применимом смысле, без понятия блокировки (например, сканирование Data Discovery) |
| `UNSUPPORTED` | Канал не контролируется |
| `NOT_VERIFIED` | Оценка не подтверждена испытанием |

В таблицах указан **целевой** уровень — гипотеза. **Подтверждённый** уровень любой ячейки сейчас — NOT_VERIFIED. Он меняется только по результату теста, записанного в TEST_RESULTS.md. Ссылка на тест вносится в ячейку.

| Локальный администратор или root, отключивший агент | Только обнаружение (пропадание heartbeat) | R-16 |

Добавление любой функции из первых четырёх строк требует отдельного ADR, оценки правовых оснований и согласования (D-08). Планируемые SMTP- и ICAP-коннекторы и Data Discovery остаются в своих фазах: D-08 их не отменяет.

Продукт не заявляет гарантированного предотвращения утечек через каналы со статусом, отличным от подтверждённого BLOCK_CAPABLE.

## 4. Контракт проверки возможностей платформы

Инварианты ниже обязательны. Поведение компилятора определено решением D-17 (C-06, вариант C) и ADR-0019: ошибка по умолчанию, понижение только по явному исключению правила.

### 4.1. Четыре величины, которые не смешиваются (AR-05)

| Величина | Поле | Значения | Кто определяет |
| --- | --- | --- | --- |
| Действие, требуемое политикой | `required_action` | MONITOR, ALERT, JUSTIFY, QUARANTINE, BLOCK | Подписанная политика |
| Фактическое действие PEP | `enforced_action` | ALLOW, BLOCK, NONE (операция не наблюдалась) | PEP — только по факту выполненной операции |
| Результат исполнения | `enforcement_status` | ENFORCED, NOT_ENFORCED(reason), NOT_OBSERVED | PEP (FAILURE_MODE_DESIGN.md §2.4) |
| Состояние контроля канала | `channel_control_state` | CONTROLLED, DEGRADED, UNCONTROLLED, UNKNOWN | Сервис агента, сервер |
| Наблюдение операции | `observation` | OBSERVED, NOT_OBSERVED | PEP |

Если PEP не загружен или не присоединён к тому, операция **не наблюдается**. Для неё нет ни вердикта PDP, ни события, поэтому гарантировать событие по каждой пропущенной операции нельзя. Потеря контроля обнаруживается по состоянию службы, драйвера, watchdog и heartbeat (FAILURE_MODE_DESIGN.md §8a) и фиксируется интервалом `CONTROL_LOST` → `CONTROL_RESTORED`.

### 4.1a. Инварианты

1. **Тихое понижение запрещено.** Действие BLOCK никогда не заменяется на MONITOR или ALERT без явной записи, видимой: (а) автору и утверждающему политики при компиляции; (б) в подписанном бандле; (в) в объяснении каждого решения; (г) в событии.
2. **Требуемое и фактическое действие разделены.** В событии всегда есть оба поля: `required_action` и `enforced_action`.
3. **Подтверждённость.** Уровень BLOCK_CAPABLE учитывается только со ссылкой на тест для данной ОС и версии агента.
4. **Потеря контроля не скрывается.** Консоль показывает канал устройства как незащищённый на всём интервале `UNCONTROLLED` или `UNKNOWN`. Отсутствие событий в этом интервале не трактуется как отсутствие операций.

### 4.2. Манифест возможностей

```text
CapabilityManifest {             // входит в подписанный пакет агента
  agent_version, platform, os_version_range,
  entries: [{ channel, operation, level, verified_by: [TestRunId] }]
}
EffectiveCapabilities {          // сообщается агентом в heartbeat
  manifest_version,
  active: [{ channel, operation, level }],   // подмножество манифеста
  missing: [{ channel, operation, reason }]  // например, DRIVER_NOT_LOADED, ENTITLEMENT_MISSING
}
```

### 4.3. Проверка при компиляции политики

Для каждого правила и каждой платформы в его области:

| Запрошено | Уровень в манифесте | Результат |
| --- | --- | --- |
| BLOCK | BLOCK_CAPABLE с `verified_by` | Принято |
| BLOCK | Иной или без подтверждения, кроме UNSUPPORTED | Ошибка `CAPABILITY_INSUFFICIENT`. Исключение: понижение до ALERT или MONITOR, только если пониженное действие проходит строку «MONITOR или ALERT» этой таблицы и у правила есть утверждённое исключение с обоснованием для этих платформы, канала и операции (ADR-0019). Применённое исключение записывается в отчёт компиляции, бандл, объяснение решения и событие и показывается в консоли |
| `on_indeterminate = BLOCK` | Иной, чем подтверждённый BLOCK_CAPABLE | Ошибка компиляции (ADR-0016). Исключение понижения основного BLOCK это правило не отменяет (D-17) |
| MONITOR или ALERT | MONITOR_ONLY или выше | Принято |
| Любое | UNSUPPORTED | Ошибка компиляции: правило не может действовать на этой платформе |

JUSTIFY и QUARANTINE на платформе без подтверждённого исполнения: правило не публикуется, автоматическое понижение запрещено (§4.1a; решение владельца от 2026-11-12). Окончательное правило — открытый вопрос (ADR-0019, DECISION_LOG.md §4).

Отчёт компиляции показывает утверждающему таблицу «правило × платформа → запрошенное и применяемое действие». Публикация без утверждения отчёта невозможна.

### 4.4. Проверка во время выполнения

Проверка при компиляции (§4.3) и потеря исполнения во время работы — разные механизмы (ADR-0019 §4). Исключения понижения не подавляют переход канала в `DEGRADED` и `ENFORCEMENT_FAILED` для операций с `required_action = BLOCK`. Неисполнение определяется по критериям FAILURE_MODE_DESIGN.md §2.4a, а не сравнением `required_action` и `enforced_action`.

1. **PEP активен, но механизм блокировки канала на устройстве отсутствует** (например, нет entitlement). Вердикт PDP не меняется: это неспособность исполнения, а не неопределённость анализа. Если требуется BLOCK (правилом или fallback), операция фактически проходит. PEP записывает `enforced_action = ALLOW` и `enforcement_status = NOT_ENFORCED(CAPABILITY_UNAVAILABLE)`, канал переходит в `DEGRADED`, отправляется событие P1 `ENFORCEMENT_FAILED`. Ложная запись `enforced_action = BLOCK` запрещена (FAILURE_MODE_DESIGN.md §2.4, INV-E1…E4).
2. **PEP не загружен или не присоединён:** вердиктов и событий по операциям нет. Сервис агента, watchdog или сервер (по отсутствию heartbeat) переводят канал в `UNCONTROLLED` или `UNKNOWN` и создают событие `CONTROL_LOST`.
3. После восстановления — событие `CONTROL_RESTORED` с длительностью интервала.
