### Network PoC (принят в составе D-12)

- **Цель:** проверить цепочку «политика → `sentinel-core` → вердикт → действие шлюза → событие» на одном канале (ICAP или SMTP) без изменения состава и критериев Windows MVP.
- **Ограничения:** не производственный код; только синтетические данные; запуск — после разрешения на начало разработки.
- **Критерий завершения:** отчёт в TEST_RESULTS.md: совместимость с выбранным прокси или MTA, задержка p95, поведение при отказе инспекции (fallback по ADR-0016).

## C-01. Состав и порядок MVP

**Контекст.** ARCH-0001: MVP = `sentinel-core`, сервер (PKI, политики), агент Windows с блокировкой USB, инциденты, консоль; сетевые каналы — на пилоте. FID: MVP = платформа → сетевой срез ICAP/SMTP с блокировкой → агент Windows только в наблюдении → блокировка на Windows. Утверждено: D-03 (первым строится `sentinel-core`), D-04 (Windows первым среди ОС, условно до Q-02), D-05 (блокирующие правила сначала в Monitor).

| Критерий | A. ARCH-0001 | B. FID | C. Гибрид |
| --- | --- | --- | --- |
| Состав | Ядро, сервер, агент Windows (блокировка USB), инциденты, консоль | Платформа, ICAP/SMTP, агент Windows (наблюдение), затем блокировка | Ядро и сервер; первая блокировка — ICAP или SMTP (один канал); агент Windows в Monitor; блокировка USB — после подписи драйвера и SPIKE-WIN-01 |
| Когда возможна первая реальная блокировка | После подписи драйвера (R-01) | Без драйвера, на шлюзе | Без драйвера, на шлюзе |
| Зависимость от R-01 и R-03 | Критическая: блокирует результат MVP | Только для конца MVP | Только для блокировки USB |
| Производительность | Риски задержки на endpoint проявляются сразу | Задержка шлюза проверяется раньше задержки endpoint | Обе — в своём порядке |
| Безопасность | Драйвер ядра в MVP | Драйвер позже; шлюз принимает поток от прокси | Как B |
| Сложность | Меньше компонентов в MVP | Больше: шлюзы + агент | Больше, чем A; меньше, чем B (один сетевой канал) |
| Влияние на MVP | Без изменений относительно ARCH-0001 | Сетевые каналы входят в MVP; агентская блокировка — последней | Сетевой канал входит в MVP; блокировка USB — критерий выхода MVP при условии подписи |
| Соответствие D-03, D-04, D-05 | Да | D-04 — да, если «Windows первым» трактуется как порядок ОС; D-05 — да | Да |

**Рекомендация:** вариант C. Он даёт проверку всей цепочки «политика → вердикт → действие → инцидент» до подписи драйвера, не нарушает D-03 и D-04 и выполняет требование D-05 «сначала Monitor». Требует ответа на вопрос, нужна ли блокировка с первого релиза (FID/OQ-06), и сведений о прокси и MTA организации (Q-05).

**Решение владельца (2026-11-11):** вариант A + Network PoC вне MVP (D-12, окончательно). ROADMAP.md остаётся в редакции ARCH-0001.

## C-03. Изоляция парсеров недоверенных форматов

**Контекст.** ADR-0003 (Accepted): агент использует `sentinel-core` напрямую; на сервере ядро вызывается в отдельном процессе (ADR-0002). FID: парсеры всегда в изолированном процессе. Этот документ **не утверждает** новую структуру процессов.

### Альтернативы

| Вариант | Описание |
| --- | --- |
| A | Парсинг в процессе сервиса агента (текущий ADR-0003) |
| B | Пул долгоживущих процессов-песочниц; сервис передаёт дескриптор файла |
| C | Отдельный процесс на каждый запрос |
| D | Гибрид: в процессе сервиса — определение типа и детекторы по уже извлечённому тексту; разбор сложных форматов (OOXML, PDF, архивы) — в пуле песочниц (B) |
| E | Песочница WebAssembly внутри процесса (например, Wasmtime) с ограничением памяти и «топлива» |

### Требования к тестированию

1. Непрерывный фаззинг каждого парсера в той же конфигурации песочницы, что и в продукте.
2. Корпус вредоносных образцов: zip-бомбы, «billion laughs» в XML внутри OOXML, PDF с циклическими ссылками, глубоко вложенные архивы.
3. Внесение сбоев: аварийное завершение, зависание и исчерпание памяти рабочего процесса. Ожидается INDETERMINATE и восстановление пула.
4. Проверка песочницы: попытки сетевого соединения, записи на диск, доступа к реестру и ключам должны отклоняться.
5. Бенчмарк p50, p95, p99 вариантов A и D на файлах 1, 10 и 100 МБ на эталонном оборудовании.

**Рекомендация:** вариант D. Безопасный код Rust исключает определённые классы ошибок памяти, но эта гарантия не распространяется на блоки `unsafe`, в том числе в зависимостях, и на FFI с библиотеками на C и C++; логические ошибки, паника и исчерпание ресурсов в парсерах сторонних форматов не исключаются. Решение — после бенчмарка.

**Решение владельца (2026-11-11):** вариант D в принципе (D-14, ADR-0018); механизм — после бенчмарка и SPIKE-WIN-01. ADR-0003 не изменяется: следствия для агента дополнены ADR-0018.

## C-06. Действие BLOCK на канале без подтверждённой блокировки

Инварианты CAPABILITY_MATRIX.md §4 действуют при любом варианте: тихое понижение запрещено, `required_action` и `enforced_action` разделены.

| Критерий | A. Автопонижение с предупреждением администратору (FID) | B. Отказ компиляции | C. Отказ по умолчанию; понижение только по явному флагу правила с обоснованием |
| --- | --- | --- | --- |
| Риск ложного чувства защищённости | Выше: предупреждение можно пропустить | Нет | Низкий: понижение — осознанное действие автора, видно утверждающему |
| Удобство единой политики для нескольких ОС | Высокое | Низкое: нужны отдельные правила | Высокое после явного решения |
| Соответствие D-08 («не заявлять предотвращение») | Только если предупреждение обязательно к подтверждению | Да | Да |
| Сложность | Низкая | Низкая | Средняя: флаг, отчёт компиляции |

**Рекомендация:** вариант C.

**Решение владельца (2026-11-11):** вариант C (D-17, ADR-0019). `on_indeterminate = BLOCK` без подтверждённого BLOCK_CAPABLE отклоняется всегда, исключение это правило не отменяет.
