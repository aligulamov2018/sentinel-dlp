## 1. Принципы

1. **Вердикт и действие разделены.** PDP вычисляет вердикт; PEP (драйвер, сервис агента, шлюз) выполняет действие.
2. **Отсутствие вердикта не равно разрешению.** INDETERMINATE обрабатывается только по явному правилу подписанной политики.
3. **Локальность.** Сервер не участвует в блокирующем пути; его недоступность не меняет решения.
4. **Ядро минимально.** В режиме ядра нет разбора файлов, правил и тяжёлых вычислений.
5. **Конечность ожиданий.** Каждое ожидание имеет таймаут; каждая очередь имеет предел; ни одна операция ОС не ждёт бесконечно.
6. **Честность гарантий.** Fail-closed заявляется только там, где он подтверждён испытанием для конкретной ОС и канала.

## 2. Контракт вердикта

### 2.1. Результат инспекции (вход PDP)

| Статус | Значение |
| --- | --- |
| `MATCH` | Детекторы нашли совпадения; приложены идентификаторы детекторов и маскированные фрагменты в пределах D-07. Target Design (D-18, Accepted 2026-11-12): возможен и при неполном покрытии — порог достигнут в разобранной части, причины неполноты сохраняются (docs/architecture/SENTINEL_CORE_DESIGN.md §4.1) |
| `NO_MATCH` | Содержимое полностью проинспектировано (полное покрытие и достоверная классификация, docs/architecture/SENTINEL_CORE_DESIGN.md §4.2), совпадений нет |
| `NOT_INSPECTED(reason)` | Содержимое не проинспектировано полностью; причина — из таблицы 2.3 |

Разделение `NO_MATCH` и `NOT_INSPECTED` заимствовано из FID/SYSTEM_ARCHITECTURE §9.1 (U-11, совместимо с D-05).

На агенте сбой изолированного разбора (D-14) даёт `NOT_INSPECTED(reason)` по таблице ADR-0018 §5. Вердикт и действие PEP определяются дальше по §2.2 и §3 без изменений.

Неполнота покрытия — свойство результата инспекции, а не статус. Её признак и причины передаются в PDP при любом статусе, в том числе при `MATCH`, и используются атомом политики `inspection.incomplete` (docs/architecture/SENTINEL_CORE_DESIGN.md §6.1).

### 2.2. Вердикт PDP

```text
Decision {
  verdict:          ALLOW | BLOCK | INDETERMINATE
  reasons:          [ReasonCode]      // обязательно непусто при INDETERMINATE
  policy_version:   u64?             // отсутствует при решении без проверенного бандла (POLICY_ABSENT, POLICY_INVALID, POLICY_EXPIRED; ИТ-05, CHG-0007)
  policy_bundle_id: hash?            // то же
  matched_rules:    [RuleId]          // включая проигравшие при разрешении конфликта
  required_action: MONITOR | ALERT | JUSTIFY | QUARANTINE | BLOCK   // действие правила
  fallback:         BLOCK | ALLOW_WITH_AUDIT   // только для INDETERMINATE
  degraded:         bool             // true при оценке политики не в состоянии CURRENT (§4.6) или без проверенного бандла (ИТ-04, CHG-0007)
  explanation:      Trace              // детерминированное объяснение
}
```

Правила:

- `verdict = BLOCK` возможен только при достоверном результате и применимом блокирующем правиле.
- Если инспекция неполная, вердикт **достоверный** (BLOCK или ALLOW), когда он одинаков при любом значении неизвестного — в том числе по условию политики на неполноту (например, «зашифрованный архив → BLOCK»); иначе INDETERMINATE (D-19; docs/architecture/SENTINEL_CORE_DESIGN.md §6.3).
- PDP детерминирован: одинаковый вход (контекст, результат инспекции, бандл) даёт байт-в-байт одинаковое решение. Часы, сеть и случайные числа в PDP не используются; время передаётся во входе.

### 2.3. Причины INDETERMINATE

| Код | Когда возникает | Где обнаруживается |
| --- | --- | --- |
| `TIMEOUT` | Анализ не уложился в бюджет времени | Сервис агента, шлюз |
| `SERVICE_UNAVAILABLE` | Драйвер не получил ответ сервиса: порт отключён, таймаут доставки | Драйвер |
| `QUEUE_SATURATED` | Превышен предел очереди запросов драйвер → сервис | Драйвер |
| `AGENT_NOT_READY` | Сервис запускается и ещё не загрузил проверенную политику | Сервис агента |
| `POLICY_ABSENT` | Нет ни одной проверенной политики (первый запуск) | PDP |
| `POLICY_INVALID` | Последний действующий бандл повреждён, а резервного нет | PDP |
| `POLICY_EXPIRED` | Истёк жёсткий срок действия политики (§4) | PDP |
| `UNSUPPORTED_FORMAT` | Формат не поддерживается парсерами | Инспекция |
| `CONTENT_ENCRYPTED` | Содержимое зашифровано, а политика не задаёт условия на это | Инспекция |
| `RESOURCE_EXHAUSTED` | Превышены лимиты размера, памяти, глубины вложенности или коэффициента распаковки | Инспекция |
| `PARSE_ERROR` | Парсер отказал на некорректных данных | Инспекция |
| `CONTENT_CHANGED` | Содержимое изменилось между анализом и применением (§7) | Сервис агента |
| `ENGINE_ERROR` | Внутренняя ошибка движка | PDP, инспекция |

Перечень расширяется только с изменением версии схемы решения. Неизвестный код PEP обрабатывает как `ENGINE_ERROR`.

### 2.4. Исполнение действия PEP (SR2-04)

Неспособность **исполнить** действие и неопределённость **анализа** — разные явления:

- неопределённость анализа — это вердикт INDETERMINATE (§2.3);
- неспособность исполнения — это результат PEP `enforcement_status`, а не вердикт PDP.

Поэтому `CAPABILITY_MISMATCH` не является причиной INDETERMINATE.

```text
EnforcementResult {                       // формирует только PEP, по факту выполненной операции
  required_action:    MONITOR | ALERT | JUSTIFY | QUARANTINE | BLOCK   // требуемое скомпилированной политикой (после исключения ADR-0019) или fallback
  requested_action:   BLOCK | —                                         // исходное действие правила; только при применённом исключении
  capability_exception_id: id | —                                       // только при применённом исключении
  enforced_action:    ALLOW | BLOCK | NONE                              // что PEP фактически сделал
  enforcement_status: ENFORCED | NOT_ENFORCED(reason) | NOT_OBSERVED
  reason:             CAPABILITY_UNAVAILABLE | PEP_ERROR | TIMEOUT_DRIVER | …
}
```

| Ситуация | `enforced_action` | `enforcement_status` | Состояние канала | Сигнал |
| --- | --- | --- | --- | --- |
| Требуется BLOCK, PEP вернул отказ ОС (например, `STATUS_ACCESS_DENIED`) | BLOCK | ENFORCED | `CONTROLLED` | Событие решения |
| Требуется BLOCK (правилом или fallback `on_indeterminate = BLOCK`), но у PEP на этом устройстве нет механизма блокировки канала (нет entitlement, нет нужного перехвата) | **ALLOW** — операция фактически прошла | NOT_ENFORCED(`CAPABILITY_UNAVAILABLE`) | `DEGRADED` | P1 `ENFORCEMENT_FAILED`; консоль показывает канал как не защищённый блокировкой |
| Требуется BLOCK, PEP пытался, но получил ошибку | Фактический результат операции ОС | NOT_ENFORCED(`PEP_ERROR`) | `DEGRADED` | P1 `ENFORCEMENT_FAILED` |
| PEP не загружен или не присоединён | NONE | NOT_OBSERVED | `UNCONTROLLED` | `CONTROL_LOST` (§8a) — не по операции |

Инварианты:

| ID | Инвариант |
| --- | --- |
| INV-E1 | `enforced_action = BLOCK` записывается только при подтверждённом отказе операции со стороны ОС |
| INV-E2 | Fallback BLOCK не применяется как «исполненный», если PEP технически не способен блокировать: фиксируется фактический результат и NOT_ENFORCED |
| INV-E3 | Неисполнение определяется не сравнением `required_action` и `enforced_action`, а критериями §2.4a для требуемого действия. Каждое неисполнение BLOCK порождает P1 `ENFORCEMENT_FAILED` и сигнал деградации; неисполнение побочного действия MONITOR или ALERT фиксируется своим механизмом; тихое понижение запрещено |
| INV-E4 | Обработка неисполнения во время выполнения не заменяет проверку при компиляции (D-17, ADR-0019). Исключение понижения не подавляет переход канала в `DEGRADED` и `ENFORCEMENT_FAILED` для операций с `required_action = BLOCK`; операции, которые после понижения требуют MONITOR или ALERT, `ENFORCEMENT_FAILED` не получают |

### 2.4a. Критерии исполнения по требуемому действию (CHG4-AR-01)

`required_action` — действие, фактически требуемое скомпилированной подписанной политикой: действие правила после применения исключения (ADR-0019) или действие fallback при INDETERMINATE. Исходный запрос BLOCK и ID исключения хранятся отдельно (`requested_action`, `capability_exception_id`).

| `required_action` | ENFORCED, если | Неисполнение |
| --- | --- | --- |
| BLOCK | `enforced_action = BLOCK` (INV-E1) | NOT_ENFORCED(reason), P1 `ENFORCEMENT_FAILED`, канал `DEGRADED` |
| MONITOR, ALERT; аудит при `ALLOW_WITH_AUDIT` | `enforced_action = ALLOW` и событие надёжно записано в локальную очередь | Потеря события — маркер `EVENTS_LOST` и `TELEMETRY_INCOMPLETE` (EVENT_PIPELINE_DESIGN.md §3.1, §3.2); `ENFORCEMENT_FAILED` не формируется |
| JUSTIFY, QUARANTINE | Не определено (Pending, DECISION_LOG.md §4) | — |

Утрата механизма блокировки канала на устройстве обнаруживается по `EffectiveCapabilities` независимо от исключений и от наличия операций, требующих BLOCK: канал переходит в `DEGRADED` с событием перехода состояния. Детерминированные сценарии — раздел 5 ADR-0019.

## 3. Fallback для INDETERMINATE

Поле `on_indeterminate` задаётся в правиле политики для пары «канал, операция»:

| Значение | Действие PEP | Сопровождение |
| --- | --- | --- |
| `ALLOW_WITH_AUDIT` (по умолчанию) | Разрешить | Событие с причиной INDETERMINATE, сигнал деградации, счётчик |
| `BLOCK` | Запретить | Событие, уведомление пользователя, сигнал деградации |

Компилятор политик принимает `on_indeterminate = BLOCK` только при одновременном выполнении условий:

1. операция помечена `protected_operation: true`;
2. задана ограниченная область: группы пользователей или устройств, классы носителей; «все пользователи всех устройств» без явного подтверждения не допускается;
3. для целевой ОС канал имеет в CAPABILITY_MATRIX.md статус BLOCK_CAPABLE с подтверждённой проверкой;
4. правило прошло период Monitor на пилотной группе: в метаданных правила есть ссылка на запись о пилоте.

Первичный кандидат — запись на съёмные носители. Fail-closed по содержимому, которое не удалось проанализировать, допускается только при явном `on_indeterminate = BLOCK`.

Уточнения CHG-0005 — **Target Design (решение D-19, Accepted 2026-11-12, OA-2)**; ADR-0016 не меняется. Согласование с §2.2 этого документа, ADR-0018 §5 и ограничением D-14 утверждено (OA-2, OA-5, OA-6) — docs/architecture/SENTINEL_CORE_DESIGN.md §12.2:

- **Чьё `on_indeterminate` применяется.** При INDETERMINATE — самое строгое `on_indeterminate` среди правил, которые могут стать победителем при каком-либо значении неизвестного (docs/architecture/SENTINEL_CORE_DESIGN.md §6.3, шаг 8). Правило, которое не может изменить исход, на fallback не влияет.
- **Разрешающий fallback против достоверного BLOCK.** Если правило с действием MONITOR или ALERT выше по приоритету, чем правило BLOCK, зависит от содержимого и имеет `on_indeterminate = ALLOW_WITH_AUDIT`, неизвестное может превратить достоверный BLOCK в разрешение по fallback. Такая пара, а также правило BLOCK с атомом неполноты ниже правила MONITOR или ALERT, — конфликт приоритетов. Компилятор и ядро при загрузке отклоняют политику с конфликтом без явного утверждения пары (docs/architecture/SENTINEL_CORE_DESIGN.md §6.7).
- **Разрешение без победителя при неполной инспекции** (`OUTCOME_INDEPENDENT_OF_UNKNOWN`) — не fallback: вердикт ALLOW достоверен при любом значении неизвестного. Подписанная запись политики `IncompleteInspectionAction` задаёт действие (MONITOR или ALERT) только для исхода «победителя нет»; значения по умолчанию в ядре нет. Итоговое требуемое действие — самое строгое среди возможных исходов, с признаком `action_certainty` (docs/architecture/SENTINEL_CORE_DESIGN.md §6.3, шаг 7).
- **Сигнал неполной инспекции** — атрибут события решения и метрика доли неполной инспекции. Это не потеря возможности канала: статус канала `DEGRADED` и событие `ENFORCEMENT_FAILED` формируются только по §2.4a.

## 4. Жизненный цикл политики и время (AR-03, SR2-01)

### 4.1. Атрибуты бандла

Каждый бандл содержит `issued_at`, `not_before`, `soft_ttl`, `hard_expiry_at` (абсолютное время), монотонную `version` и идентификатор ключа подписи. Разрешающие отступления — исключения и break-glass — имеют собственные `expires_at` и `max_offline_validity`, не больше `soft_ttl`.

### 4.2. Модель угрозы времени

| Нарушитель | Возможности | Следствие для дизайна |
| --- | --- | --- |
| Н1 — пользователь без прав администратора | Не меняет системное время и файлы агента (стандартные права ОС; NOT VERIFIED для каждой ОС) | Достаточно мер §4.4 |
| Н2 — локальный администратор | Переводит часы, многократно перезагружает устройство без сети, копирует и восстанавливает **старое валидное** состояние агента, откатывает снимок ВМ | HMAC не защищает от восстановления старого состояния; нужна отдельная защита от отката |

Н2 также может остановить или удалить агент (T-02, R-16). Поэтому цель — не «защитить срок от администратора», а гарантировать: **манипуляции временем не продлевают разрешающие отступления и не отключают запрещающие правила**.

### 4.3. Целостность и защита от отката — разные свойства

| Свойство | Вопрос | Механизм | Достаточен ли против Н2 |
| --- | --- | --- | --- |
| Целостность | Не подделано ли состояние | HMAC или подпись ключом агента | Да, против подделки |
| Свежесть (защита от отката) | Не подменено ли состояние более старой валидной копией | Монотонный счётчик вне контроля Н2: NV-счётчик TPM (исследование, §4.8) или подписанное время сервера при связи | HMAC — **нет**. Без счётчика TPM — нет в офлайне |

Вывод: без подтверждённого аппаратного счётчика агент **не может установить достоверное прошедшее время в офлайне** против Н2. Дизайн исходит из этого.

### 4.4. Источники времени и учёт

| Источник | Доверие | Использование |
| --- | --- | --- |
| Подписанное время сервера (`server_time`, `nonce` агента, подпись) | Доверенное и свежее | Опорная точка `T_ref`; единственный офлайн-независимый источник свежести |
| Монотонные часы ОС в пределах одного непрерывного запуска сервиса | Доверенные в пределах запуска; подделка требует компрометации ядра (вне модели, R-16) | Срок разрешающих отступлений внутри запуска |
| Настенные часы ОС | Недоверенные против Н2 | Только как нижняя оценка прошедшего времени |
| NV-счётчик TPM | Не подтверждено | Исследование §4.8 |

Сохраняемая запись `time_state` (`t_ref_server`, `wall_at_ref`, `elapsed_since_ref`, `last_wall_seen`, `boot_count_since_ref`, `mac`) защищена HMAC и служит для сигналов и состояний, но **не является доказательством свежести**.

Учёт после перезапуска без связи с сервером:

```text
elapsed = max(saved.elapsed_since_ref + T_boot_penalty,
              wall_now − saved.wall_at_ref)
```

- `T_boot_penalty` (Proposed: 1 ч) добавляется при **каждом** запуске сервиса без свежего времени сервера. Поэтому многократные офлайн-перезагрузки с переводом часов всё равно продвигают `elapsed`: не более `soft_ttl / T_boot_penalty` запусков до состояния `STALE`.
- **`T_boot_penalty` — эвристика, а не гарантия защищённого времени.** Она действует, только пока сохранённая запись `time_state` не откатывается. Восстановление старой валидной записи (копия файла, образ диска, снимок ВМ) возвращает и старый `elapsed`. Против отката разрешающие отступления защищает только §4.5 (INV-T2), и только при перезапуске (§4.7.1).
- Запись сохраняется сразу после запуска и далее каждые `T_persist`.
- Настенное время меньше `last_wall_seen` → событие P1 `CLOCK_ROLLBACK`; срок не продлевается.

### 4.5. Разрешающие отступления не переживают перезапуск в офлайне

Главная мера против отката (SR2-01):

1. Исключения и break-glass, действующие в офлайне, хранятся **только в памяти** работающего сервиса. Срок отсчитывается по монотонным часам текущего запуска.
2. После перезапуска сервиса или перезагрузки без свежего времени сервера все разрешающие отступления **недействительны** до повторной проверки на сервере.
3. Офлайн-код break-glass содержит `nonce` текущего запуска сервиса и действителен только в этом запуске, не дольше `T_bg` по монотонным часам. Восстановление старой записи или старого кода не даёт нового разрешения.
4. Исключение после подтверждённого аппаратного счётчика (§4.8) — только отдельным решением владельца.

Следствие: восстановление старого валидного `time_state`, перевод часов и многократные перезагрузки, **сопровождаемые перезапуском сервиса**, не продлевают разрешающие отступления. Они могут продлить только состояние `CURRENT` или `STALE` как сигнал. Запрещающие правила от времени не зависят.

**Граница меры.** Мера опирается на то, что откат сопровождается перезапуском сервиса. Восстановление снимка ВМ вместе с оперативной памятью возвращает работающий процесс сервиса без перезапуска. Тогда восстанавливаются и разрешающие отступления в памяти (§4.7.1).

### 4.6. Состояния срока действия

| Состояние | Условие | Поведение |
| --- | --- | --- |
| `CURRENT` | Свежее время сервера в текущем запуске, `elapsed < soft_ttl`, оценка текущего времени < `hard_expiry_at` | Штатное применение, включая разрешающие отступления |
| `STALE` | `elapsed >= soft_ttl`, `hard_expiry_at` не наступил | Запрещающие и контролирующие правила действуют; исключения с истёкшим `max_offline_validity` отключены; сигнал `POLICY_STALE` |
| `TIME_UNVERIFIABLE` | Нет свежего времени сервера в текущем запуске, **или** `time_state` отсутствует, повреждён, не прошёл HMAC, **или** обнаружен разрыв времени (§4.7) | Запрещающие и контролирующие правила действуют; все разрешающие отступления, кроме break-glass текущего запуска (§4.5 п. 3), отключены; сигнал `TIME_UNVERIFIABLE`; событие P1 при повреждении (`TIME_STATE_INVALID`) |
| `EXPIRED` | Оценка текущего времени ≥ `hard_expiry_at` | §4.9 (Proposed) |

**Поведение при невозможности установить достоверное прошедшее время** — состояние `TIME_UNVERIFIABLE`:

- **нет глобальной блокировки:** ОС загружается, операции вне области защищаемых не задерживаются;
- **нет глобального разрешения:** запрещающие правила и fallback защищаемых операций действуют как обычно;
- **нет продления разрешающих отступлений:** они отключены (§4.5).

### 4.7. Разрывы времени

| Событие | Признак | Реакция |
| --- | --- | --- |
| Сон, гибернация | Скачок настенного времени при сохранении `boot_id` | Учёт через `wall_now − wall_at_ref`; если время ушло назад — `CLOCK_ROLLBACK` |
| Откат снимка ВМ без памяти или восстановление образа диска | Неожиданное возвращение к старому `time_state`; сервер видит повтор `seq` или старое `boot_count` | Агент сам не всегда отличает это от штатной работы. Обнаруживается сервером при связи (дубликаты ниже `low_watermark`, `REPLAY_SUSPECTED`). Сервис запускается заново, поэтому разрешающие отступления не восстанавливаются (§4.5) |
| Восстановление снимка ВМ **вместе с RAM** | Процесс сервиса продолжает работу с момента снимка; монотонные часы гостя продолжаются со значения в снимке; возможен скачок настенного времени при синхронизации гостя; меняется VM Generation ID (если гипервизор его поддерживает) | См. §4.7.1. Разрешающие отступления в памяти восстанавливаются без перезапуска — INV-T2 против этого не защищает |
| Большой скачок вперёд | `wall_now − wall_at_ref` > порога | Безопасное направление: срок истекает раньше; событие P2 |

#### 4.7.1. Восстановление снимка ВМ вместе с RAM (SR3-04)

**Что восстанавливается.** Состояние диска и памяти на момент снимка:
- работающий процесс сервиса;
- исключения и break-glass в памяти вместе с `nonce` запуска;
- монотонные часы сервиса;
- `time_state` на диске.

С точки зрения сервиса перезапуска не было.

**Последствия для разрешающих отступлений.**
- Исключение, действовавшее в момент снимка, снова действует после каждого восстановления. Остаток его срока по монотонным часам тоже восстанавливается.
- Многократно восстанавливая один снимок, Н2 может многократно использовать одно разрешающее отступление.
- Мера §4.5 «только в текущем запуске» против этого **не защищает**, потому что запуск восстанавливается целиком.
- Запрещающие и контролирующие правила не затрагиваются (INV-T1): снимок не создаёт новых разрешений, а лишь возвращает существовавшие.

**Что может обнаружить агент** (все пункты — NOT VERIFIED):

| Признак | Источник | Ограничения |
| --- | --- | --- |
| Смена VM Generation ID | Windows: устройство `\\.\VmGenerationCounter` и `IOCTL_VMGENCOUNTER_READ`, в том числе в режиме ожидания изменения (Microsoft Learn) | Только на гипервизорах, предоставляющих идентификатор; поддержку парка гипервизоров нужно проверить. Аналог для Linux и macOS не исследован |
| Скачок настенного времени относительно монотонного при той же загрузке | Синхронизация времени гостя после восстановления | Зависит от настроек гостевых инструментов; без синхронизации скачка нет |
| Сервер и агент: идентичность передачи | Ответ на первую передачу после восстановления (EVENT_PIPELINE_DESIGN.md §3.1, §4.3 п. 6): `batch_no < last_batch_no` → `STALE_BATCH`; тот же `batch_no` с другим digest → `BATCH_INTEGRITY_CONFLICT`. В обоих случаях флаг агента, событие безопасности и процедура восстановления; новые события с повторно выданными `seq` не принимаются за дубликаты | Не обнаруживается, если тот же `batch_no` пришёл с совпадающим digest (первоначальный ACK: состояние воспроизведено полностью и данные передачи совпадают) или если между снимком и восстановлением не было обработанных передач — тогда события после снимка теряются без следа (R-24). Обнаружение — только после связи |

**Мера при обнаружении** (Proposed, требует проверки):
- при смене VM Generation ID или при скачке времени выше порога агент сбрасывает все разрешающие отступления в памяти, как при перезапуске (§4.5 п. 2);
- при ответе `STALE_BATCH` или `BATCH_INTEGRITY_CONFLICT` на текущую передачу агент делает то же самое: это признак отката состояния;
- агент переходит в `TIME_UNVERIFIABLE` до получения свежего времени сервера и порождает событие P1 `VM_ROLLBACK_SUSPECTED`.

Пока механизм не подтверждён испытаниями, он не считается защитой.

**Граница гарантий.** Если пользователь управляет гипервизором (например, локальная ВМ на собственном компьютере), защитить офлайн-разрешения от восстановления памяти нельзя: гипервизор полностью контролирует гостя. **Решение владельца от 2026-11-11:** на ВМ с гипервизором под управлением пользователя или с недоверенным гипервизором привилегированные офлайн-исключения и офлайн break-glass **запрещены по умолчанию**. Если агент обнаружил виртуализацию, а доверие к гипервизору не подтверждено администратором (атрибут устройства в инвентаре), устройство считается недоверенным. Механизм — Proposed, обнаружение виртуализации — NOT VERIFIED. Это решение не утверждает поведение после `hard_expiry_at` и правила офлайн break-glass в целом — они остаются Pending Approval. Остаточный риск — R-24, уровень High.

**TPM и vTPM.**
- Поведение vTPM при восстановлении снимка, в том числе возможность отката NV-счётчика вместе со снимком, не исследовано — NOT VERIFIED (§4.8).
- Аппаратный TPM на физическом устройстве не участвует в снимках ВМ, но применимость к парку тоже NOT VERIFIED.

### 4.8. Исследование: защита от отката на основе TPM (DLP-ENDPOINT-020)

Статус — **исследование, NOT VERIFIED**. Не считается подтверждённым механизмом.

- **Идея:** NV-счётчик TPM 2.0 увеличивается при каждом сохранении `time_state`; значение счётчика входит в подписанную запись; запись с несовпадающим значением отвергается как старая.
- **Вопросы:** доступность TPM 2.0 в парке (Q-02); ресурс записи NV и допустимая частота увеличения; поведение vTPM при откате снимка ВМ; Linux (`/dev/tpmrm0`); отсутствие TPM на macOS и альтернативы; права доступа сервиса; восстановление после очистки TPM.
- **Результат исследования:** отчёт и, при положительном результате, отдельное предложение владельцу. До этого действуют §4.5–§4.6.

### 4.9. Поведение после `hard_expiry_at` — **Proposed, требует отдельного утверждения владельцем**

- Запрещающие и контролирующие правила продолжают действовать.
- Исключения, break-glass и иные разрешающие отступления прекращают действовать.
- Условие, требующее данных с истёкшим сроком (например, индекса EDM), даёт INDETERMINATE(`POLICY_EXPIRED`) с fallback правила.
- Глобального fail-open нет.

### 4.10. Восстановление после длительной изоляции

1. При восстановлении связи агент получает подписанное время сервера со своим `nonce`, обновляет `T_ref` и сбрасывает `elapsed` и `boot_count_since_ref`.
2. Сервер сравнивает применённую версию бандла с актуальной и передаёт новую.
3. Исключения и break-glass не восстанавливаются автоматически — требуется новая выдача.
4. В heartbeat передаются длительность изоляции, число офлайн-запусков и события `CLOCK_ROLLBACK`.

### 4.11. Аварийное восстановление без неопределённой блокировки ОС

- Fail-closed действует только для защищаемых операций (§3). Загрузка ОС, системные операции и операции вне области не блокируются ни при каком состоянии времени.
- Офлайн-код аварийного отключения перехвата — «запрос — ответ», привязка к устройству и `nonce` запуска, одноразовый, двойное подтверждение при выпуске, аудит.
- Загрузка Windows в безопасном режиме без запуска драйвера как путь восстановления — NOT VERIFIED, проверяется в SPIKE-WIN-01.

### 4.12. Инварианты безопасности (SR2-01)

| ID | Инвариант |
| --- | --- |
| INV-T1 | Запрещающие и контролирующие правила не зависят от достоверности времени |
| INV-T2 | Разрешающее отступление в офлайне действует не дольше одного непрерывного запуска сервиса и не дольше своего срока по монотонным часам этого запуска. **Условие:** откат сопровождается перезапуском сервиса. Восстановление снимка ВМ вместе с RAM возвращает запуск целиком, и INV-T2 против него не выполняется (§4.7.1) |
| INV-T3 | **Если сохранённая запись `time_state` не откатывалась**, каждый запуск без свежего времени сервера продвигает `elapsed` не меньше чем на `T_boot_penalty`. При откате записи INV-T3 не гарантируется: `T_boot_penalty` — эвристика, а не защищённое время (§4.4) |
| INV-T4 | Целостность записи времени (HMAC) не считается доказательством её свежести |
| INV-T5 | Никакое состояние времени не приводит к глобальной блокировке или глобальному разрешению |

| Вид отката | INV-T1 | INV-T2 | INV-T3 | INV-T4 | INV-T5 | Обнаружение |
| --- | --- | --- | --- | --- | --- | --- |
| Перевод часов, перезагрузки без отката записи | Да | Да | Да | Да | Да | `CLOCK_ROLLBACK`; рост `elapsed` |
| Восстановление старой записи `time_state` (файл, образ диска, снимок без RAM) с перезапуском | Да | Да | **Нет** | Да | Да | Сервер при связи: повтор `seq`, старое `boot_count` |
| Восстановление снимка ВМ вместе с RAM | Да | **Нет** | **Нет** | Да | Да | VM Generation ID и скачок времени — NOT VERIFIED; сервер — постфактум по `INTEGRITY_CONFLICT` |
| Пользователь управляет гипервизором | Вне модели | **Нет** | **Нет** | Вне модели | Вне модели | Не гарантируется |

Последняя строка выходит за модель нарушителя Н2: гипервизор полностью контролирует гостя, поэтому никакие гарантии агента, а не только связанные со временем, не заявляются. Свежесть времени в офлайне против Н2 не обеспечивается ни в одной строке без подтверждённого аппаратного счётчика (§4.8, NOT VERIFIED). Поведение после `hard_expiry_at` (§4.9) и офлайн break-glass (§4.5 п. 3, §4.11) остаются **Pending Approval** и ревизией 4 не меняются.

### 6.2. Fallback-таблица драйвера

Сервис передаёт драйверу при подключении компактную таблицу «класс операции → BLOCK или ALLOW» для защищаемых операций: например, «запись на том съёмного носителя, не входящего в белый список». Драйвер применяет её только при отказе связи с сервисом.

- Таблица не содержит контентных правил.
- Сохранение таблицы между перезагрузками для применения до старта сервиса и её защита от изменения локальным администратором — **NOT VERIFIED**, вопрос SPIKE-WIN-01.
- Если таблица недоступна, драйвер разрешает операцию и считает такие случаи. Гарантия fail-closed в этом интервале не заявляется.

### 6.3. Bootstrap-политика

Поставляется в подписанном пакете агента и действует до получения первой политики с сервера. По умолчанию (**Proposed**): `ALLOW_WITH_AUDIT` для всех операций. Fail-closed включается только конфигурацией установки, утверждённой организацией.

## 7. Сценарии

| Сценарий | Ожидаемое поведение | Что подтверждает испытание |
| --- | --- | --- |
| **Startup.** ОС загружается, драйвер активен раньше сервиса | Операции идут по fallback-таблице драйвера, если её сохранение подтверждено; иначе разрешаются со счётчиком | Не возникает зависаний загрузки; поведение совпадает с документированным |
| **Offline.** Нет связи с сервером | Решения не меняются; события копятся; по `soft_ttl` → `STALE`, по `hard_expiry_at` → `EXPIRED` (§4) | Блокировка работает без сервера; сигналы появляются в заданный момент |
| **Crash.** Сервис аварийно завершился | Драйвер получает `STATUS_PORT_DISCONNECTED` и переходит в `NO_CLIENT`; watchdog перезапускает сервис | Нет взаимоблокировки; защищаемые операции идут по fallback |
| **Crash loop.** Повторяющиеся сбои | После N перезапусков за M минут агент переходит в `DEGRADED` без дальнейших попыток; оповещение администратору | Нет бесконечного цикла; рабочее место остаётся работоспособным |
| **Timeout.** Анализ большого файла | INDETERMINATE(TIMEOUT) и fallback; анализ прерывается, ресурсы освобождаются | Операция ОС не ждёт дольше `T_drv` |
| **Recovery.** Сервис восстановлен | Повторная проверка бандла, переход в `ACTIVE`, отправка накопленных счётчиков | Счётчики совпадают с числом обработанных fallback-операций |
| **Policy tamper.** Подмена файла политики | Проверка подписи не проходит; используется последняя проверенная копия; событие | Подмена не меняет решений |

### 7.1. Watchdog, восстановление и break-glass

- **Watchdog** — независимый от сервиса механизм: восстановление средствами службы ОС или отдельный процесс. Выбор — после SPIKE-WIN-01 по результатам TC-D15-01 (D-15). Перезапуск с экспоненциальной задержкой; предел N перезапусков за M минут; затем `DEGRADED`.
- **Ограничение деградации.** В `DEGRADED` агент не меняет действия политики самостоятельно: защищаемые операции идут по fallback, остальные — по правилам.
- **Break-glass** — исключение для пользователя, устройства или канала:
  - выпускается сервером, подписан, ограничен по области и времени (не более T_bg);
  - для офлайн-устройства выпускается код по схеме «запрос — ответ», привязанный к устройству и `nonce` текущего запуска сервиса, одноразовый; после перезапуска сервиса код недействителен (§4.5);
  - создание требует права `break_glass.issue`; для высокорисковых областей (все устройства, все каналы, срок больше порога) — двойное подтверждение двумя разными лицами;
  - каждое применение фиксируется событием `BREAK_GLASS_USED`;
  - после `hard_expiry_at` политики break-glass не действует (§4.9).
- **Аварийное отключение перехвата** (`MAINTENANCE`) отличается от break-glass: это платформенная мера восстановления при массовом сбое. Требует подписанной команды, двойного подтверждения и аудита; агент сообщает о состоянии в heartbeat.

## 8. Ограничения Windows minifilter

Проверено по Microsoft Learn 2026-11-10 (документация, не испытание):

- `FltSendMessage` с `Timeout = NULL` ждёт **бесконечно**. Это запрещено: всегда передаётся конечный отрицательный (относительный) таймаут.
- `STATUS_TIMEOUT` возвращается как **код успеха**, поэтому проверка через `NT_SUCCESS()` его пропускает. Обработчик сравнивает статус явно.
- Обрабатываются все документированные коды: `STATUS_SUCCESS`, `STATUS_TIMEOUT`, `STATUS_PORT_DISCONNECTED`, `STATUS_INSUFFICIENT_RESOURCES`, `STATUS_BUFFER_OVERFLOW`, `STATUS_THREAD_IS_TERMINATING`. Любой иной код ведёт к fallback.
- `FltSendMessage` вызывается при IRQL ≤ APC_LEVEL.
- Группы порядка загрузки: FSFilter Content Screener — 260000–269999 («предотвращение создания определённых файлов или содержимого»), FSFilter Activity Monitor — 360000–389999. Высоту выделяет Microsoft по заявке. Выбор группы — вопрос SPIKE-WIN-01.

Требования дизайна, не проверенные испытанием (**NOT VERIFIED**):

- Во время ожидания ответа драйвер не держит блокировок, которые нужны сервису или файловой системе.
- Собственный ввод-вывод сервиса агента исключается из перехвата, иначе чтение файла сервисом вызывает повторный запрос и взаимоблокировку. Способ — исключение по процессу клиента порта или передача сервису дескриптора, открытого драйвером. Выбирается в SPIKE-WIN-01.
- Paging I/O, операции ядра и операции с флагами, не допускающими ожидания, не задерживаются.
- Число одновременно ожидающих запросов ограничено (`Q_max`). При переполнении — fallback без ожидания.
- **Блокировка записи по содержимому.** В pre-create содержимое ещё неизвестно. Уровни L1–L3 и их гарантии — §8.1. Пока вариант L3 не выбран и не испытан, контентная блокировка записи на USB имеет статус NOT VERIFIED.
- **MTP/WPD-устройства** (телефоны, камеры) не являются файловыми томами и не видны minifilter. Для них нужен отдельный механизм, например device-level deny (§10).

### 8.1. Уровни контроля съёмных носителей (AR-06)

Это три разных механизма. Ни один из них не заменяет другой, и подтверждение одного не означает подтверждения остальных.

| Уровень | Что предотвращается | Механизм (Windows) | Гарантия | Статус |
| --- | --- | --- | --- | --- |
| L1. Device-level deny | Подключение недоверенного устройства | Политики установки устройств, PnP-фильтрация (DLP-ENDPOINT-017) | Устройство недоступно ОС; содержимое не анализируется | NOT VERIFIED |
| L2. Блокировка операции до записи | Открытие файла с правом записи или создание файла на томе вне белого списка | Minifilter, pre-create (DLP-ENDPOINT-002) | Запись не начинается; содержимое не анализируется | NOT VERIFIED; первый кандидат BLOCK_CAPABLE |
| L3. Контентная блокировка с гарантией неизменности проверенных байтов | Запись конкретного содержимого | Теневая запись или буферизация с фиксацией только после вердикта по тем же байтам (DLP-ENDPOINT-019) | Записывается только проанализированное содержимое | **NOT VERIFIED**; R-15 — существенный остаточный риск |

До завершения SPIKE-WIN-01 подтверждённая контентная блокировка записи на USB не заявляется. Варианты «сопоставление с источником» и «инспекция при cleanup с удалением» **не дают гарантии L3**: первый не связывает вердикт с записываемыми байтами, второй допускает окно экспозиции.

## 8a. Обнаружение потери контроля канала (AR-05)

Если minifilter не загружен или не подключён к тому, PEP **не наблюдает** операции. Для таких операций нет ни вердикта PDP, ни события. Число пропущенных операций неизвестно. Поэтому потеря контроля обнаруживается по состоянию компонентов, а не по операциям.

| Источник сигнала | Что проверяется | Кто проверяет |
| --- | --- | --- |
| Сервис агента | Драйвер загружен; экземпляр фильтра присоединён к каждому тому съёмного носителя; порт подключён | Сервис, каждые `T_detect` (Proposed: 30 с) и по событиям подключения томов |
| Watchdog | Сервис жив и отвечает | Watchdog |
| Heartbeat | Агент передаёт `channel_control_state` по каждому каналу | Сервер |
| Отсутствие heartbeat | Агент молчит дольше 3 интервалов (Proposed) | Сервер: состояние `UNKNOWN` |

Перечисление экземпляров фильтра из пользовательского режима (`FilterFindFirst`, `FilterInstanceFindFirst`) — способ проверки NOT VERIFIED, подтверждается в SPIKE-WIN-01.

Состояния контроля канала: `CONTROLLED`, `DEGRADED` (PEP работает в fallback), `UNCONTROLLED` (PEP не наблюдает операции), `UNKNOWN` (нет связи с агентом). Переходы фиксируются событиями P1 `CONTROL_LOST` и `CONTROL_RESTORED`; второе содержит длительность интервала без контроля.

## 9. Параметры

Все значения — **Proposed**; утверждаются после SPIKE-WIN-01 и нагрузочных испытаний.

| Параметр | Предлагаемое значение | Основание |
| --- | --- | --- |
| `T_drv` — ожидание драйвером ответа сервиса | 3 с | Верхняя граница задержки операции записи |
| `T_insp` — бюджет анализа в сервисе | 2 с, строго меньше `T_drv` | Вердикт должен успеть вернуться до таймаута драйвера |
| `Q_max` — предел ожидающих запросов | 64 | Защита от исчерпания потоков |
| `soft_ttl` | 72 ч, по накопленному времени (§4.3) | Обнаружение длительной изоляции |
| `hard_expiry_at` | `issued_at` + 30 суток | FID/NFR-REL-02 предлагает автономность не менее 7 суток (U-12) |
| `T_persist` — период сохранения `time_state` | 5 мин | Ограничение потери учтённого времени при сбое |
| `T_boot_penalty` — минимальный прирост `elapsed` за запуск без свежего времени сервера | 1 ч | Продвижение времени при многократных офлайн-перезагрузках (§4.4) |
| `T_detect` — проверка присоединения фильтра | 30 с | Обнаружение потери контроля (§8a) |
| Watchdog: N перезапусков за M минут | 3 за 10 мин | Предотвращение цикла сбоев |
| `T_bg` — максимальный срок break-glass | 8 ч | Ограничение окна отступления |

## 10. Device-level deny недоверенных USB-устройств

Отдельное исследование по D-05 (DLP-ENDPOINT-017). Это независимый слой: запрет подключения недоверенных устройств средствами ОС. Он **не заменяет** контентную DLP.

- **Windows.** Политики установки устройств и PnP-фильтрация.
- **Linux.** Авторизация USB через sysfs/udev (подход USBGuard).
- **macOS.** AUTH_MOUNT для накопителей; прочие классы устройств ограничены.

Все варианты — NOT VERIFIED. VID, PID и серийный номер подделываются (T-26), поэтому белый список устройств не является строгой аутентификацией.

## 12. Кэш вердиктов и TOCTOU

- Ключ кэша: SHA-256 проинспектированного содержимого, версия бандла, версия набора детекторов, хеш контекста (канал, область). Смена политики полностью инвалидирует кэш.
- Вердикт применяется только к тем же байтам, которые были проанализированы. Для записи на носитель это выполнимо только при теневой записи или инспекции буфера перед фиксацией (§8). Иначе TOCTOU остаётся остаточным риском (R-15).
- Изменение файла после анализа выявляется по идентификатору файла и признакам модификации — **NOT VERIFIED**. При обнаружении: INDETERMINATE(CONTENT_CHANGED).

| R-24 | Без аппаратного счётчика агент не может доказать свежесть состояния времени в офлайне. Восстановление снимка ВМ вместе с RAM возвращает разрешающие отступления без перезапуска; при управлении гипервизором пользователем защита невозможна. Откат не обнаруживается, если состояние воспроизведено полностью и данные первой передачи совпадают с уже обработанной или если после снимка не было обработанных передач (§4.7.1, §4.12) |

## 15. Требования к SPIKE-WIN-01

Результат — отчёт в TEST_RESULTS.md (будет создан с первыми результатами) и обновление CAPABILITY_MATRIX.md. Это не производственный код.

1. Выбрать группу порядка загрузки и подготовить заявку на высоту.
2. Сравнить варианты контентной блокировки записи по гарантии L3 (§8.1): связь вердикта с записываемыми байтами, окно экспозиции, задержка, совместимость с Проводником, `robocopy` и офисными приложениями.
3. Подтвердить блокировку без анализа содержимого для незарегистрированного тома.
4. Выбрать способ исключения собственного I/O сервиса и показать отсутствие взаимоблокировки под нагрузкой.
5. Проверить сохранение fallback-таблицы драйвера между перезагрузками и её защиту.
6. Пройти FI-D05-01…04, 10, 11 в тестовой подписи.
7. Измерить задержку p50/p95/p99 решения без анализа и с анализом файлов 1, 10 и 100 МБ.
8. Проверить совместимость минимум с Microsoft Defender и с EDR, используемым в организации.
9. Определить поведение для MTP/WPD и подготовить рекомендации по device-level deny.
10. Проверить обнаружение потери контроля (§8a) и загрузку в безопасном режиме как путь восстановления (§4.7).
11. Для изоляции разбора (D-14, ADR-0018): проверить рабочий процесс с ограниченным токеном или AppContainer и Job Object, измерить задержку IPC; пройти TC-D14-01…03 и TC-D14-05.
12. Для процессов агента (D-15): сравнить восстановление средствами Windows Service и отдельный watchdog по TC-D15-01.

Критерий завершения: по каждому пункту есть измерение или явно зафиксированная невозможность. Сроки устанавливаются после ответа на Q-08.
