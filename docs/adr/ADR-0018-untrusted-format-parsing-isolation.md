# ADR-0018. Изоляция разбора недоверенных форматов на агенте

| Атрибут | Значение |

| Версия | 1 |
| Дата | 2026-11-11 |

| Связанные документы | ADR-0003, ADR-0016, ADR-0015 (Proposed), docs/architecture/FAILURE_MODE_DESIGN.md §2, §3, docs/architecture/DECISION_PROPOSAL_C01_C06.md (раздел C-03), docs/DECISION_LOG.md §2 |

## Контекст

Сервис агента — привилегированный процесс. Он хранит ключи и проверенную политику, подключён к порту драйвера и исполняет решения PEP. По ADR-0003 агент использует `sentinel-core` напрямую, то есть разбор файлов, подготовленных нарушителем, выполняется в этом же процессе. Ошибка парсера, паника, зависание или исчерпание памяти затрагивают весь сервис. Эксплуатация парсера даёт нарушителю права сервиса (T-05).

Rust (ADR-0003) снижает этот риск, но не устраняет его:

- гарантии безопасности памяти распространяются только на безопасный код Rust;
- они не распространяются на блоки `unsafe`, в том числе в сторонних crates, на FFI с библиотеками на C и C++ и на ошибки компилятора или стандартной библиотеки;
- логические ошибки, паника, бесконечные циклы и исчерпание ресурсов не исключаются ни в каком коде.

Решение принимается на синхронном пути: время анализа ограничено `T_insp` (FAILURE_MODE_DESIGN.md §9). Межпроцессный вызов добавляет задержку. Её величина не измерена.

## Рассмотренные варианты

Полный анализ — DECISION_PROPOSAL_C01_C06.md, раздел C-03.

| Вариант | Суть | Итог |
| --- | --- | --- |
| A | Разбор в процессе сервиса | Отклонён: сбой парсера затрагивает привилегированный процесс |
| B | Пул долгоживущих рабочих процессов для всего разбора | Основа варианта D |
| C | Отдельный процесс на каждый запрос | Отклонён для синхронного пути: стоимость создания процесса (NOT VERIFIED) |
| **D** | **Гибрид: в сервисе — определение типа, декодирование простого текста, детекторы и PDP; разбор сложных форматов — в пуле рабочих процессов** | **Принят в принципе** |
| E | WebAssembly-песочница в процессе сервиса | Не выбран: процесс общий, зрелость сборки парсеров в WASM не подтверждена |

## Решение

### 1. Принцип

Рискованный разбор недоверенных форматов не выполняется в привилегированном процессе агента.

| Где | Что выполняется |
| --- | --- |
| Сервис агента | Определение класса файла только по сигнатуре в начале файла (magic bytes), без разбора структуры контейнера (DLP-DETECTION-001); декодирование простого текста TXT и CSV с лимитом размера (DLP-DETECTION-002); детекторы и маскирование над извлечённым текстом (DLP-DETECTION-004…006); PDP |
| Рабочий процесс разбора | Уточнение подтипа контейнеров по их структуре (например, ZIP → DOCX или XLSX по центральному каталогу и `[Content_Types].xml`); разбор контейнеров и сложных форматов: OOXML (DLP-DETECTION-002) и PDF (DLP-DETECTION-003) в объёме MVP. Любой формат, добавляемый в следующих фазах, по умолчанию относится сюда |

Перечень «выполняется в сервисе» закрытый. Он расширяется только изменением этого ADR.

### 2. Объём

ADR не расширяет набор форматов Windows MVP. В MVP агент разбирает только форматы DLP-DETECTION-001…003. Архивы (DLP-DETECTION-007), устаревшие форматы (DLP-DETECTION-013) и OCR (DLP-DETECTION-012) остаются в своих фазах. Формат вне объёма даёт `NOT_INSPECTED(UNSUPPORTED_FORMAT)`.

Область ADR — Endpoint Agent (DLP-ENDPOINT-021). Механизм изоляции для `sentinel-gateway`, `sentinel-scanner`, серверной инспекции и CLI `sentinel-scan` этот ADR не определяет. Он решается при проектировании этих компонентов.

### 3. Граница с `sentinel-core`

1. `sentinel-core` остаётся единственной реализацией определения типа, извлечения текста, детекторов, маскирования и PDP. Альтернативная, упрощённая или отдельно поддерживаемая реализация разбора для агента не создаётся.
2. Рабочий процесс — хост-процесс агента. Он вызывает функции извлечения `sentinel-core` из той же версии пакета агента, что и сервис. Версия ядра и версия протокола проверяются при установлении канала.
3. От API ядра требуется одно: разбор (извлечение) и анализ (детекторы, PDP) доступны отдельными вызовами. Промежуточный результат — извлечённый текст, метаданные формата или `NOT_INSPECTED(reason)` — сериализуется в версионируемом формате. Контракт вердикта (ADR-0016) не меняется. Формат промежуточного результата — часть версионируемого API `sentinel-core`, чтобы сервис и рабочий процесс использовали одно определение. Формат определяется при переходе DLP-ENDPOINT-021 в Designed.
4. Канал IPC, пул рабочих процессов, профили песочниц и их управление — код Endpoint Agent, а не `sentinel-core`.
5. Другие потребители ядра используют тот же API. Результат разбора одного файла одинаков при прямом вызове `sentinel-core` в тестовом стенде и через рабочий процесс; это проверяется golden-тестом. В продукте рискованный разбор в процессе сервиса не выполняется.

### 4. Обязательные требования к механизму

**Права рабочего процесса.** Рабочий процесс:

- не имеет прав сервиса;
- не имеет доступа к сети;
- не может писать на диск;
- не имеет доступа к ключам, конфигурации и локальной очереди агента и к порту драйвера;
- не имеет доступа к ключам реестра агента и не может писать в реестр Windows (чтение общесистемных разделов, нужное загрузчику ОС, не исключается);
- не может создавать дочерние процессы.

Ограничения устанавливаются механизмами ОС, а не кодом парсера.

Кандидаты механизмов (все — NOT VERIFIED):

| ОС | Ограничение прав | Ограничение ресурсов |
| --- | --- | --- |
| Windows | Ограниченный токен или AppContainer | Job Object (в том числе лимит активных процессов); запрет дочерних процессов — также атрибутом политики дочерних процессов при создании процесса |
| Linux | seccomp, namespaces | cgroups v2, `setrlimit` |
| macOS | sandbox-профиль | `setrlimit` |

Механизм, который закрывает только одну сторону, песочницей не считается. Job Object ограничивает ресурсы и время жизни процесса, но сам по себе не сужает права токена. seccomp ограничивает системные вызовы, но не память и не время.

**Лимиты ресурсов.** Все значения — Proposed, перенесены из DECISION_PROPOSAL_C01_C06.md. Лимиты памяти и времени устанавливаются средствами ОС.

| Лимит | Значение (Proposed) |
| --- | --- |
| Размер входного объекта для синхронного анализа | 100 МБ |
| Суммарный распакованный объём | 500 МБ |
| Коэффициент распаковки (в том числе для контейнера OOXML) | 100:1 |
| Глубина вложенности встроенных объектов | 5 |
| Объём извлечённого текста | 50 МБ |
| Память рабочего процесса | 512 МБ |
| Время разбора | Доля бюджета `T_insp`, оставляющая время на IPC, детекторы и PDP; значение — по TC-D14-05 |
| Число рабочих процессов | max(1, min(ядра CPU / 2, 4)) |
| Перезапуски рабочего процесса | Ограниченное число за интервал; затем сигнал деградации |

**IPC.**

- Локальный канал с ACL: подключаются только сервис агента и рабочие процессы пула.
- Версия протокола проверяется при установлении канала. Размеры сообщений ограничены.
- Содержимое передаётся без копирования через дескриптор или разделяемую память только для чтения. Способ — NOT VERIFIED.
- Сервис проверяет ответ рабочего процесса как недоверенные данные: схему, размеры, соответствие запросу.
- Извлечённый текст — чувствительные данные. Он не записывается в журналы и на диск и не покидает канал. Аварийные дампы рабочего процесса подчиняются DATA_PROTECTION_DESIGN.md §9.

### 5. Поведение при отказах

Сбой разбора — это результат инспекции, а не вердикт и не действие. Три величины не смешиваются:

| Величина | Кто формирует | Источник правил |
| --- | --- | --- |
| Результат инспекции `NOT_INSPECTED(reason)` | Сервис агента по ответу или отказу рабочего процесса | FAILURE_MODE_DESIGN.md §2.1, §2.3 |
| Вердикт PDP: достоверный или INDETERMINATE(reason) | PDP | FAILURE_MODE_DESIGN.md §2.2 |
| Действие PEP при INDETERMINATE | PEP по `on_indeterminate` подписанной политики | ADR-0016, FAILURE_MODE_DESIGN.md §3 |

| Ситуация | Результат инспекции |
| --- | --- |
| Рабочий процесс аварийно завершился | `NOT_INSPECTED(ENGINE_ERROR)` |
| Разбор не уложился во время | `NOT_INSPECTED(TIMEOUT)` |
| Превышен лимит памяти, размера, распаковки или вложенности | `NOT_INSPECTED(RESOURCE_EXHAUSTED)` |
| Некорректные данные формата | `NOT_INSPECTED(PARSE_ERROR)` |
| Пул недоступен; версии протокола не совпали; ответ не прошёл проверку | `NOT_INSPECTED(ENGINE_ERROR)` |
| Формат вне объёма | `NOT_INSPECTED(UNSUPPORTED_FORMAT)` |

Дальше действуют неизменённые правила:

- Если у правила есть условие на `NOT_INSPECTED`, PDP выносит достоверный вердикт.
- Иначе вердикт — INDETERMINATE с той же причиной.
- Действие PEP задаёт `on_indeterminate`. По умолчанию это `ALLOW_WITH_AUDIT`. `BLOCK` допустим только при условиях ADR-0016 и D-17 (ADR-0019).

Изоляция не вводит новых причин INDETERMINATE и не меняет fallback.

Неспособность PEP исполнить действие — отдельная величина `enforcement_status` (FAILURE_MODE_DESIGN.md §2.4). Сбой рабочего процесса сам по себе не меняет `channel_control_state`: PEP продолжает работу. Повторные сбои дают событие и сигнал деградации.

### 6. Выбор механизма

Механизм выбирается по результатам бенчмарка вариантов A и D (TC-D14-05) и SPIKE-WIN-01. Выбор утверждает владелец. Если задержка варианта D окажется недопустимой для синхронного пути, вопрос возвращается владельцу. Рискованный разбор не переносится в привилегированный процесс без нового решения.

## Последствия

- ADR-0003 не изменяется. Его положение «агент использует `sentinel-core` напрямую» для агента уточняется этим ADR: сервис вызывает ядро для анализа, а рискованный разбор выполняет рабочий процесс. Мера из рисков ADR-0003 «при необходимости — изолированный процесс с внешним парсером» для агента становится обязательной в форме изолированного процесса с тем же `sentinel-core`.
- Появляется дополнительная роль агента: рабочий процесс разбора. Её подпись, обновление и восстановление учитываются в D-15.
- Добавочная задержка IPC на синхронном пути учитывается в R-11 и измеряется TC-D14-05.
- Нарушение границы песочницы — новый риск R-25.
- Фаззинг парсеров (TC-SEC-04) выполняется в той же конфигурации песочницы, что и в продукте.
- ENDPOINT_AGENT_DESIGN.md с деталями механизма создаётся после SPIKE-WIN-01 (D-15).

## Риски

| Риск | Мера |
| --- | --- |
| Выход за границу песочницы (R-25) | Ограничения механизмами ОС с двух сторон (права и ресурсы); TC-D14-03; фаззинг в продуктовой конфигурации |
| Задержка IPC превышает бюджет синхронного решения (R-11) | Передача без копирования; пул вместо процесса на запрос; замер TC-D14-05; решение владельца при превышении |
| Атака на сервис через ответы рабочего процесса | Проверка ответа как недоверенных данных; версия протокола; ACL канала; TC-D14-04 |
| Намеренный вызов сбоев для обхода через fail-open (T-14) | Неизменённые правила ADR-0016; условия политики на `NOT_INSPECTED`; метрики доли INDETERMINATE |
| Профили песочниц различаются на трёх ОС | Отдельная проверка на каждой ОС; уровень изоляции не заявляется для ОС без испытания |

## Статус проверки

Механизм не реализован и не испытан. Применимость на Windows — NOT VERIFIED до SPIKE-WIN-01 и TC-D14-01…06; на Linux и macOS — до SPIKE-LNX-01 и SPIKE-MAC-01. Лимиты — Proposed.

## Действия

1. Включить в план SPIKE-WIN-01 проверку ограниченного токена или AppContainer вместе с Job Object и замер IPC.
2. Выполнить бенчмарк TC-D14-05 и представить владельцу выбор механизма.
3. При переходе DLP-ENDPOINT-021 в Designed определить формат промежуточного результата и протокол IPC.
