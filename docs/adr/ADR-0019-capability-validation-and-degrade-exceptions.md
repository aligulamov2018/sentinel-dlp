## Контекст

Одна политика может действовать на нескольких ОС и каналах, а возможность блокировки у них разная (CAPABILITY_MATRIX.md §2). Ветка FID предлагала автоматически понижать BLOCK до наблюдения с предупреждением администратору (FID/DLP-POLICY-005). Предупреждение можно пропустить, и правило будет выглядеть как блокирующее, хотя не блокирует. D-08 запрещает заявлять предотвращение через каналы без подтверждённой блокировки.

Инварианты CAPABILITY_MATRIX.md §4.1a уже обязательны: тихое понижение запрещено, `required_action` и `enforced_action` разделены. Не было определено, что делает компилятор.

## Рассмотренные варианты

| Вариант | Суть | Итог |
| --- | --- | --- |
| A | Автопонижение с предупреждением | Отклонён: высокий риск ложного чувства защищённости |
| B | Всегда ошибка компиляции | Отклонён: единую политику для нескольких ОС пришлось бы делить на отдельные правила |
| **C** | **Ошибка по умолчанию; понижение только по явному исключению правила** | **Принят** |

## Решение

### 1. Проверка при компиляции

Для каждого правила и каждой пары «платформа, канал, операция» в его области компилятор использует только манифест возможностей с подтверждением `verified_by` (CAPABILITY_MATRIX.md §4.2). `EffectiveCapabilities` из heartbeat при компиляции не используются.

| Запрошено | Уровень в манифесте | Действующее исключение | Результат |
| --- | --- | --- | --- |
| BLOCK | BLOCK_CAPABLE с `verified_by` | — | Принято |
| BLOCK | Не BLOCK_CAPABLE с `verified_by` и не UNSUPPORTED | Нет | Ошибка `CAPABILITY_INSUFFICIENT`; бандл не создаётся |
| BLOCK | Не BLOCK_CAPABLE с `verified_by` и не UNSUPPORTED | Есть, область совпадает | Понижение до `effective_action` исключения, если это действие само проходит проверку CAPABILITY_MATRIX.md §4.3 для области (MONITOR или ALERT — уровень MONITOR_ONLY или выше); иначе ошибка. Запись во всех местах из п. 3 |
| `on_indeterminate = BLOCK` | Иной, чем BLOCK_CAPABLE с `verified_by` | Любое | Ошибка компиляции. Исключение это правило не отменяет; остальные условия ADR-0016 также обязательны |
| Любое | UNSUPPORTED | Любое | Ошибка компиляции; исключение не применяется |

### 2. Исключение понижения

Исключение — единственный способ понизить BLOCK.

```text
CapabilityException {
  exception_id
  rule_id
  scope:            { platform, channel, operation }  // ровно одно сочетание; шаблон «все» запрещён
  requested_action: BLOCK
  effective_action: ALERT | MONITOR                   // должно само проходить проверку CAPABILITY_MATRIX.md §4.3
  justification:    text                              // обязательно
  author, approver                                    // approver ≠ author
  approval_ref
  expires_at                                          // Proposed: обязательность и предельный срок
}
```

- Исключение без обоснования или без утверждения — ошибка компиляции. Самоутверждение запрещено.
- Исключение действует только в своей области. Для другой платформы, канала или операции нужно отдельное исключение.
- Исключение касается только основного действия правила. На `on_indeterminate` оно не влияет.
- Компиляция повторяется при изменении манифеста возможностей. Если для области подтвердили BLOCK_CAPABLE, отчёт помечает исключение как лишнее. Если подтверждение исчезло, правило без исключения перестаёт компилироваться, и отчёт это показывает.

### 3. Видимость

Применённое исключение видно:

1. в отчёте компиляции — таблица «правило × платформа → запрошенное и применяемое действие, ID исключения»; публикация без утверждения отчёта невозможна;
2. в подписанном бандле;
3. в объяснении каждого решения;
4. в событии: `required_action` — действие после понижения; отдельно `requested_action = BLOCK` и `capability_exception_id` (§4);
5. в консоли: канал по этому правилу отображается как не защищённый блокировкой;
6. в отчётах о покрытии.

Состав полей события и бандла фиксируется в DATA_MODEL.md. **Зависимость:** изменение схемы данных (`CapabilityException`, поля `requested_action` и `capability_exception_id` в событии и бандле) обязательно до начала реализации DLP-POLICY-015. В CHG-0004 DATA_MODEL.md не изменяется.

### 4. Значения полей и критерии исполнения (CHG4-AR-01)

`required_action` и `enforced_action` принадлежат разным пространствам значений: первое — действие политики (MONITOR, ALERT, JUSTIFY, QUARANTINE, BLOCK), второе — фактический результат операции (ALLOW, BLOCK, NONE). Потеря исполнения не определяется сравнением этих значений.

| Поле события | Значение |
| --- | --- |
| `required_action` | Действие, фактически требуемое скомпилированной подписанной политикой для этой операции: действие правила после применения исключения или действие fallback при INDETERMINATE |
| `requested_action` | Исходное действие правила до понижения (BLOCK). Заполняется только при применённом исключении |
| `capability_exception_id` | ID утверждённого исключения. Заполняется только при применённом исключении |
| `enforced_action` | Фактический результат операции: ALLOW, BLOCK или NONE (FAILURE_MODE_DESIGN.md §2.4) |
| `enforcement_status` | ENFORCED, NOT_ENFORCED(reason) или NOT_OBSERVED — по критериям таблицы ниже |

Критерии исполнения определяются по `required_action`:

| `required_action` | ENFORCED, если | Нарушение и сигнал |
| --- | --- | --- |
| BLOCK (из правила или fallback `on_indeterminate = BLOCK`) | `enforced_action = BLOCK` при подтверждённом отказе ОС (INV-E1) | Операция прошла: `enforced_action = ALLOW`, NOT_ENFORCED(reason), P1 `ENFORCEMENT_FAILED`, канал `DEGRADED` |
| MONITOR или ALERT, в том числе после понижения | Операция обработана по политике (`enforced_action = ALLOW` — штатный результат), и событие с этим действием надёжно записано в локальную очередь агента | Неисполнение побочного действия — отдельный критерий: событие вытеснено или не записано → маркер `EVENTS_LOST` и режим `TELEMETRY_INCOMPLETE` (EVENT_PIPELINE_DESIGN.md §3.1, §3.2), при полном отказе хранилища — EVENT_PIPELINE_DESIGN.md §4.9 и R-22; создание оповещения на сервере для ALERT проверяется конвейером инцидентов. `ENFORCEMENT_FAILED` не формируется |
| Аудит при fallback `ALLOW_WITH_AUDIT` | Как для MONITOR | Как для MONITOR |
| JUSTIFY, QUARANTINE | Критерии не определены (открытый вопрос ниже) | — |

**Утрата BLOCK_CAPABLE на устройстве** обнаруживается независимо от исключений и от того, требует ли какая-либо операция BLOCK:

- агент сообщает канал в `EffectiveCapabilities.missing` (CAPABILITY_MATRIX.md §4.2);
- канал переходит в `DEGRADED` с событием перехода состояния (DLP-ENDPOINT-018) — один раз на переход, а не на каждую операцию;
- консоль показывает канал как не защищённый блокировкой.

`ENFORCEMENT_FAILED` формируется только для операций, у которых `required_action = BLOCK`. Операции с `required_action` MONITOR или ALERT, в том числе после понижения по исключению, не получают `ENFORCEMENT_FAILED`.

Исключения не подавляют ни переход канала в `DEGRADED`, ни `ENFORCEMENT_FAILED` для операций, требующих BLOCK. Потеря исполнения не создаёт исключений и не меняет скомпилированную политику.

| | Исключение при компиляции | Потеря исполнения во время работы |
| --- | --- | --- |
| Природа | Запланированное и утверждённое решение политики | Отказ или отсутствие механизма на устройстве |
| Где обнаруживается | Отчёт компиляции, бандл | Heartbeat (`EffectiveCapabilities`), PEP по операции |
| Сигналы | `requested_action` и `capability_exception_id` в событии; консоль | Переход канала в `DEGRADED`; P1 `ENFORCEMENT_FAILED` только при `required_action = BLOCK` |
| Правила | Этот ADR | CAPABILITY_MATRIX.md §4.4; FAILURE_MODE_DESIGN.md §2.4, §2.4a, INV-E1…E4 |

### 5. Детерминированные сценарии

Вход задан полностью; ожидаемый результат однозначен. Сценарии проверяются TC-D17-04 и TC-D17-05.

| № | Вход | Ожидаемый результат |
| --- | --- | --- |
| 1 | Правило MONITOR; совпадение; локальная очередь доступна | `required_action = MONITOR`, `enforced_action = ALLOW`, ENFORCED; событие записано; `ENFORCEMENT_FAILED` нет |
| 2 | Правило ALERT; совпадение; локальная очередь доступна | `required_action = ALERT`, `enforced_action = ALLOW`, ENFORCED; событие с ALERT записано; на сервере создано оповещение; `ENFORCEMENT_FAILED` нет |
| 3 | Правило BLOCK с утверждённым исключением → ALERT для этой платформы, канала и операции; совпадение | `required_action = ALERT`, `requested_action = BLOCK`, `capability_exception_id` заполнен, `enforced_action = ALLOW`, ENFORCED; `ENFORCEMENT_FAILED` нет |
| 4 | Правило ALERT; совпадение; квота класса в локальной очереди исчерпана, событие вытеснено до отправки | `ENFORCEMENT_FAILED` нет; на сервер доставлен маркер `EVENTS_LOST`, покрывающий `seq` события (EVENT_PIPELINE_DESIGN.md §3.1) |
| 5 | Платформа с подтверждённым BLOCK_CAPABLE; правило BLOCK; ОС отказала в операции | `required_action = BLOCK`, `enforced_action = BLOCK`, ENFORCED |
| 6 | На устройстве утрачен механизм блокировки канала; в политике правило R1 (BLOCK) и правило R2 (BLOCK, понижено исключением до ALERT); по операции совпадает R1 | Канал `DEGRADED`, одно событие перехода; по операции: `required_action = BLOCK`, `enforced_action = ALLOW`, NOT_ENFORCED(`CAPABILITY_UNAVAILABLE`), P1 `ENFORCEMENT_FAILED` |
| 7 | Условия сценария 6; по операции совпадает только R2 | Канал `DEGRADED` (тот же переход); по операции: `required_action = ALERT`, `requested_action = BLOCK`, ID исключения, `enforced_action = ALLOW`, ENFORCED; `ENFORCEMENT_FAILED` нет |
| 8 | Механизм блокировки утрачен; в политике для канала нет правил, требующих BLOCK | Канал `DEGRADED`, событие перехода, консоль показывает канал как не защищённый блокировкой; `ENFORCEMENT_FAILED` нет |
| 9 | Механизм блокировки утрачен; вердикт INDETERMINATE; `on_indeterminate = BLOCK` | `required_action = BLOCK` (fallback), `enforced_action = ALLOW`, NOT_ENFORCED(`CAPABILITY_UNAVAILABLE`), P1 `ENFORCEMENT_FAILED` (как TC-D08-08) |

## Открытый вопрос

Действия JUSTIFY и QUARANTINE на платформе без подтверждённой блокировки решением D-17 не определены: D-17 и таблица CAPABILITY_MATRIX.md §4.3 касаются BLOCK, MONITOR и ALERT. Вопрос остаётся Pending (DECISION_LOG.md §4).

До решения действует правило владельца от 2026-11-12: если исполнение JUSTIFY или QUARANTINE для платформы, канала и операции не подтверждено, правило не публикуется; автоматическое понижение запрещено. Проверка — TC-D17-06.

## Последствия

- CAPABILITY_MATRIX.md §4.3 приводится к этому ADR. ADR-0016 не изменяется: правило об `on_indeterminate = BLOCK` уже входит в него и здесь подтверждено как не отменяемое исключением.
- Автопонижение из FID/DLP-POLICY-005 не переносится. Остальная часть кандидата — политики каналов — покрывается DLP-POLICY-001 и DLP-POLICY-015.
- Единая политика для нескольких ОС остаётся возможной: понижение — явное, ограниченное и видимое.
- Правила BLOCK для каналов без подтверждённой блокировки не компилируются до появления подтверждения или исключения. Пример — контентная блокировка записи на USB (L3) до SPIKE-WIN-01 (R-15).

| Риск | Мера |

| Злоупотребление исключениями: массовое понижение BLOCK | Область из одного сочетания; обоснование; утверждающий не автор; отчёт и консоль; метрика числа исключений; T-22 |
