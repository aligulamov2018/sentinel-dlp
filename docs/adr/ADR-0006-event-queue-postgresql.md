# ADR-0006. Конвейер событий в MVP: без внешнего брокера, очереди в PostgreSQL

| Атрибут | Значение |
| --- | --- |
| Назначение | Определить доставку событий от агентов и асинхронную обработку на сервере |
| Версия | 4.1 (уточнения по ревью AR-01, AR-02, AR-04, SR2-02, SR2-03, SR3-01…SR3-03, SR4-01; статус не меняется) |
| Дата | 2026-11-11 |
| Статус | Accepted with constraints |
| Решение владельца | D-06 (DECISION_LOG.md), 2026-11-10 |
| Связанные документы | ADR-0005, docs/architecture/EVENT_PIPELINE_DESIGN.md |
| Затронутые компоненты | Endpoint Agent (локальная очередь), модуль `ingest` и воркеры `sentinel-server` |
| Происхождение | ARCH-0001 §8; конфликтует с FID/ADR-005 (NATS JetStream), разрешено приоритетом D-06 — RES-02 |

## Контекст

Агент должен накапливать события без связи и доставлять их без потерь значимых событий безопасности. Сервер должен обрабатывать их асинхронно, согласованно с транзакциями записи. Масштаб не определён (Q-01); каждый дополнительный компонент с состоянием усложняет эксплуатацию в изолированном ЦОД.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Kafka | Зрелость, масштаб | Эксплуатационная сложность, ещё один кластер |
| NATS JetStream | Один бинарный файл, журнал с повторным чтением | Ещё один компонент с состоянием; пропускная способность и восстановление в наших условиях не измерены |
| RabbitMQ | Маршрутизация | Хуже подходит для журнала с повторным чтением |
| **Очереди в PostgreSQL** | Нет новой зависимости; транзакционная согласованность с записью | Ограниченная пропускная способность |

## Решение

В MVP внешнего брокера нет.

- **Агент:** локальная очередь в SQLite в режиме WAL с шифрованием; пакетная отправка по gRPC поверх mTLS.
- **Доставка:** at-least-once. Агент удаляет событие только после ACK; сервер отправляет ACK исключительно после успешной фиксации транзакции.
- **Дедупликация:** глобальная по `(endpoint_id, agent_epoch, seq)` через реестр квитанций и `low_watermark`; приём одного агента сериализуется блокировкой строки состояния; границы гарантий после очистки квитанций документированы (EVENT_PIPELINE_DESIGN.md §4).
- **Сервер:** transactional outbox; атомарный захват заданий через `FOR UPDATE SKIP LOCKED` с арендой по `clock_timestamp()` и fencing-токеном `lease_token`; короткие транзакции захвата, продления и завершения, обработка вне транзакции; восстановление заданий с истёкшей арендой; ограниченные повторы; «отравленные» задания в состоянии `dead`. Fencing гарантируется только для изменений в PostgreSQL (EVENT_PIPELINE_DESIGN.md §5).
- **Перегрузка:** backpressure и приоритет значимых событий безопасности над диагностической телеметрией.
  - Окно последовательности привязано к подтверждённому прогрессу (`low_watermark`) и одинаково для событий и маркеров.
  - Квоту `MAX_PENDING` обходит только голова очереди `low_watermark + 1`; остальные события пропуска проходят квоту.
  - Маркеры потерь имеют отдельные лимиты (EVENT_PIPELINE_DESIGN.md §4.4–§4.5, §4.10).
- **Заявления о потере** неизменяемы; позднее поступление событий фиксируется отдельными связанными записями.
- **Маркер потерь занимает слот первого потерянного события** («надгробие», EVENT_PIPELINE_DESIGN.md §3.1, §4.5). Он объявляет непрерывный диапазон не длиннее `MAX_LOSS_SPAN` и продвигает `low_watermark` одним шагом. Слотом может быть только гарантированно неотправленное событие, а в режиме `TELEMETRY_INCOMPLETE` — также событие с окончательным повторяемым отказом. Каждая передача пакета получает монотонный `batch_no` и `batch_digest`, который сервер вычисляет по полученным байтам. Устаревшие передачи отбрасываются; тот же номер с другим содержимым — `BATCH_INTEGRITY_CONFLICT`; каждый ответ связан с передачей (SR4-01).
- **Расширяемость:** серверная обработка скрыта за интерфейсом `EventQueue`. NATS JetStream остаётся кандидатом по результатам замеров и ответа на Q-01, но не обязательной зависимостью.

Exactly-once processing не обещается.

### Рассмотренные варианты маркера потерь (SR3-02, ревизия 4)

| Вариант | Суть | Почему не выбран или выбран |
| --- | --- | --- |
| Маркер на новом `seq` (ревизия 3) | Маркер получает следующий `seq` и объявляет диапазон до себя | Отклонён. Скачок `marker_seq` не ограничен (контрпример CE-2). Ограничение окном останавливает честного агента после долгой изоляции: маркер оказывается за окном |
| **Маркер в слоте первого потерянного события** | Маркер занимает `seq` первого вытесненного неотправленного события | **Выбран** (решение по SR3-02 от 2026-11-11). Скачок невозможен по построению; маркер в голове очереди всегда помещается в окно; продвижение за один шаг |
| Отдельная нумерация маркеров `loss_seq` | Маркеры вне пространства `seq`, с собственным счётчиком; окно применяется к объявленному диапазону | Не выбран: затрагивает больше документов и протокол; равноценен по корректности. Сохраняется как альтернатива на случай, если реализация надгробий в агенте окажется невозможной |

## Последствия

- Обработчики outbox идемпотентны.
- Нагрузочные испытания определяют предел MVP до пилота.
- Шифрование локальной очереди требует выбора механизма (SQLCipher или шифрование полей ключом, защищённым средствами ОС) — Pending verification.

## Риски

| Риск | Мера |
| --- | --- |
| Пропускная способность PostgreSQL недостаточна | Замеры; интерфейс `EventQueue`; пересмотр ADR |

| Потеря событий при переполнении диска агента | Резерв места для событий безопасности и маркеров, маркеры потерь, режим `TELEMETRY_INCOMPLETE` (EVENT_PIPELINE_DESIGN.md §3–§3.2) |
