# ADR-0016. Контракт вердикта PDP и поведение PEP при отказах

| Атрибут | Значение |
| --- | --- |
| Назначение | Зафиксировать разделение «вердикт PDP / действие PEP», трёхзначный контракт вердикта и правила fail-open/fail-closed |
| Версия | 4 (уточнения по ревью AR-03, AR-05, AR-06, SR2-01, SR2-04, SR3-04; статус не меняется) |
| Дата | 2026-11-11 |
| Статус | Accepted with constraints |
| Решение владельца | D-05 (DECISION_LOG.md), 2026-11-10 |
| Связанные документы | docs/architecture/FAILURE_MODE_DESIGN.md, docs/architecture/CAPABILITY_MATRIX.md, ADR-0004, docs/THREAT_MODEL.md |
| Затронутые компоненты | Policy Decision Point (`sentinel-core`), Endpoint Agent (сервис и драйвер), `sentinel-gateway`, компилятор политик |

## Контекст

Агент и шлюзы обязаны принимать решение локально, без сервера и с ограниченным временем. Анализ может не дать достоверного результата: таймаут, неподдерживаемый формат, исчерпание лимитов, сбой сервиса, недостоверная политика. Если считать такой случай разрешением, возникает канал обхода (T-14). Если запрещать всё неизвестное, растёт риск отказа в обслуживании и остановки работы пользователей.

## Рассмотренные варианты

1. Двузначный вердикт ALLOW/BLOCK; отсутствие ответа равно ALLOW.
2. Двузначный вердикт; отсутствие ответа равно BLOCK.
3. **Трёхзначный вердикт ALLOW / BLOCK / INDETERMINATE с машиночитаемыми причинами; действие при INDETERMINATE задаётся подписанной политикой отдельно для каждого канала.**

## Решение

Вариант 3.

1. PDP возвращает только вердикт и объяснение и не выполняет действий. PEP (драйвер, сервис, шлюз) выполняет действие.
2. INDETERMINATE всегда сопровождается одной или несколькими причинами из перечня FAILURE_MODE_DESIGN.md §2.
3. Действие PEP при INDETERMINATE берётся из поля `on_indeterminate` подписанной политики для конкретного канала и операции. Отсутствие вердикта никогда не приравнивается к ALLOW неявно.
4. Значение `BLOCK` в `on_indeterminate` допустимо только для операций, явно помеченных как защищаемые, с заданной областью действия, на платформе, где блокировка этого канала подтверждена (CAPABILITY_MATRIX.md, статус BLOCK_CAPABLE и проверка выполнена). Прежде всего это запись на съёмные носители.
5. Для остальных операций используется утверждённый fail-open: разрешение с аудитом и сигналом деградации защиты.
6. Недоступность сервера не влияет на локальное решение.
7. Повреждённый или неподписанный бандл политики отвергается. Используется последняя проверенная действующая политика либо отдельно утверждённый fallback.
8. В режиме ядра контентный анализ запрещён.

## Последствия

- Компилятор политик проверяет допустимость `on_indeterminate=BLOCK` и запрещает тихое понижение действия (CAPABILITY_MATRIX.md §4).
- Fail-closed определяется **областью операции** (канал, группа, устройство), а не классом данных. При INDETERMINATE класс данных неизвестен, поэтому правило вида «fail-closed для строго конфиденциальных данных» технически невыполнимо и заменено этим требованием.
- Гарантия fail-closed не заявляется для интервалов, когда драйвер не способен обеспечить её автономно: загрузка ОС до старта сервиса, отключённый драйвер, MTP/WPD-устройства. См. FAILURE_MODE_DESIGN.md §5–§7.
- Все блокирующие правила сначала работают в режиме Monitor на представительной пилотной группе.
- Целостность записи времени не считается доказательством её свежести. Разрешающие отступления в офлайне действуют только в текущем запуске сервиса — при условии, что откат сопровождается перезапуском. Восстановление снимка ВМ вместе с RAM эту меру обходит (FAILURE_MODE_DESIGN.md §4.7.1). Каждый запуск без свежего времени сервера продвигает учёт времени, но это эвристика: при откате сохранённой записи она не действует. При недостоверном времени нет ни глобальной блокировки, ни глобального разрешения (FAILURE_MODE_DESIGN.md §4, INV-T1…T5). Защита от отката на основе TPM — исследование. Поведение после `hard_expiry_at` остаётся Proposed до утверждения владельцем.
- Неспособность PEP исполнить действие — не причина INDETERMINATE, а результат исполнения `NOT_ENFORCED`. Ложная запись `enforced_action = BLOCK` запрещена (FAILURE_MODE_DESIGN.md §2.4, INV-E1…E4).
- Если PEP не загружен, операции не наблюдаются, и вердикта нет. Это состояние обнаруживается как потеря контроля канала, а не как INDETERMINATE (FAILURE_MODE_DESIGN.md §8a).
- Для USB различаются L1 (device-level deny), L2 (блокировка операции до записи) и L3 (контентная блокировка с гарантией неизменности проверенных байтов). L3 не заявляется до SPIKE-WIN-01 (R-15).

## Риски

| Риск | Мера |
| --- | --- |
| Атакующий намеренно вызывает INDETERMINATE (большой файл, запароленный архив, перегрузка) и пользуется fail-open | Fail-closed для защищаемых операций; метрики доли INDETERMINATE; сигнал деградации; T-14 |
| Fail-closed вызывает отказ в обслуживании | Узкая область защищаемых операций; break-glass; лимиты очереди; T-09, T-14 |
| Параметры таймаутов и сроков действия политик не измерены | Значения в FAILURE_MODE_DESIGN.md §9 имеют статус Proposed до SPIKE-WIN-01 и нагрузочных тестов |

## Статус проверки

Механизмы не реализованы. Применимость к Windows — NOT VERIFIED до SPIKE-WIN-01; к Linux и macOS — до SPIKE-LNX-01 и SPIKE-MAC-01.
