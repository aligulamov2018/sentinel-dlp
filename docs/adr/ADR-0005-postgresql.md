## Контекст

Нужны транзакции между политиками, аудитом и инцидентами, секционирование событий по времени, работа on-premises и в изолированном контуре без лицензионных ограничений. Масштаб (Q-01) не определён.

## Рассмотренные варианты

1. PostgreSQL.
2. Коммерческие СУБД.
3. Распределённые SQL-СУБД (CockroachDB, YugabyteDB).
4. Документные СУБД.

## Решение

PostgreSQL — единственная обязательная СУБД. Мажорная версия фиксируется при создании каркаса сервера: поддерживаемая сообществом на эту дату; конкретная версия — NOT VERIFIED.

Обязательные ограничения:

- События секционируются по **серверному времени приёма**, а не по времени агента. Иначе агент с неверными часами записывал бы события в старые секции (EVENT_PIPELINE_DESIGN.md §6).
- Глобальная дедупликация не опирается на `UNIQUE(event_id)` в секционированной таблице. Используется отдельный реестр квитанций (EVENT_PIPELINE_DESIGN.md §4).
- Модули обращаются только к своим таблицам (ADR-0001); у каждого модуля отдельная роль БД с минимальными правами.
- Схема меняется только версионированными миграциями с откатом.

## Обоснование

Зрелость, транзакции, декларативное секционирование, распространённость у заказчиков, отсутствие лицензионных отчислений, одна технология для политик, аудита и очередей.

## Последствия

- Объём событий ограничен возможностями одного кластера PostgreSQL; предел измеряется нагрузочными тестами (TEST_STRATEGY.md, TC-D06-08).
- HA требует репликации и процедуры переключения (DLP-CORE-009).
- Резервные копии содержат чувствительные метаданные и защищаются по DATA_PROTECTION_DESIGN.md §7.
