# ADR-0001. Стиль серверной архитектуры: модульный монолит

| Атрибут | Значение |
| --- | --- |
| Назначение | Зафиксировать стиль построения серверной части Sentinel DLP |
| Версия | 1 |
| Дата | 2026-11-10 |
| Статус | Accepted |
| Решение владельца | D-02 (DECISION_LOG.md), согласовано 2026-11-10 |
| Связанные требования | CLAUDE.md §3.1, §6; ARCH-0001 §5, §8 |
| Затронутые компоненты | Management Server, Policy Engine (компилятор), Incident Management, Integrations |

## Контекст

Серверная часть должна разворачиваться on-premises, в том числе в изолированном (air-gapped) ЦОД, без обязательного Kubernetes. Число endpoint-ов на пилоте и в эксплуатации ещё не определено (вопрос Q-01). Команда небольшая. Правила проекта требуют простой, контролируемой архитектуры без необоснованных инфраструктурных зависимостей.

## Рассмотренные варианты

1. **Микросервисы**: отдельные сервисы регистрации, политик, приёма событий, инцидентов и интеграций.
2. **Модульный монолит**: один серверный процесс с жёсткими границами модулей. Ресурсоёмкие и сетевые роли вынесены в отдельные процессы.

## Решение

Вариант 2. Серверная часть — один бинарь `sentinel-server` с внутренними модулями (`enrollment`, `policy`, `ingest`, `incident`, `audit`, `authz`, `integrations`). Отдельными процессами поставляются только:

- `sentinel-scanner` — Data Discovery, масштабируется горизонтально;
- `sentinel-gateway` — ICAP- и SMTP-точки контроля, размещаются рядом с прокси и MTA.

## Обоснование

- Одна транзакционная граница с PostgreSQL: публикация политики, аудит и изменение инцидента выполняются атомарно, без распределённых транзакций.
- Меньше компонентов для развёртывания, обновления, резервного копирования и мониторинга в ЦОД заказчика.
- Модуль можно выделить в сервис позже, если замеры покажут необходимость. Обратный путь — слияние микросервисов — значительно дороже.

## Последствия

- Модули взаимодействуют через внутренние интерфейсы Go, а не через сеть.
- Модуль не обращается к таблицам другого модуля напрямую — только через его интерфейс. Это проверяется линтером импортов в CI (инструмент будет выбран при создании каркаса сервера).
- Горизонтальное масштабирование сервера возможно только в режиме нескольких одинаковых экземпляров без собственного состояния. Это закладывается в дизайн с самого начала.

## Риски

| Риск | Мера |
| --- | --- |
| Размывание границ модулей со временем | Контроль импортов в CI, обязательное ревью изменений межмодульных интерфейсов |
| Рост нагрузки на приём событий выше возможностей одного процесса | Приём событий за интерфейсом очереди; пересмотр в рамках ADR-0006 по замерам пилота |

## Условия пересмотра

Измеренная нагрузка, которую нельзя обработать несколькими экземплярами монолита, или требование независимого жизненного цикла одного из модулей.
